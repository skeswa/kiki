# Daemon

`kkd` is a single user-scoped daemon, opt-in per repository via `kk init`. It is a coordinator, not a terminal host: one user-scoped daemon, many threads, thin clients over stable IPC, and no ownership of what is drawn inside a pane. Terminals live in a separate, dedicated Herdr server that `kkd` starts, verifies, observes, and never trusts as an authority. [Terminal runtime](terminal-runtime.md) defines that boundary; this chapter covers the daemon's side of it.

## Lifecycle

- One `kkd` per user.
- First-run bootstrap: the first `kk` invocation installs and starts `kkd` as a per-user service — a launchd user agent on macOS, a systemd user unit on Linux. `kk` never forks `kkd` from the invoking terminal. `kkd` and the dedicated Herdr server it starts therefore run outside the terminal application's own job and process tree, so quitting the terminal application ends neither them nor any agent. State files in `~/.config/kiki/` are created with mode `0700`; the gRPC socket and credential files are mode `0600`.
- Reboot survival: the service manager restarts `kkd` after a crash, logout, or reboot. Recovery on restart reads sqlite; threads survive crashes and reboots. Agent processes do not survive a reboot; their threads read `TerminalMissing` afterwards.
- Per-thread `ThreadController` actors supervise durable lifecycle sagas and die only after a thread is closed or destroyed coherently; cross-cutting components include the op-log watcher, cascade orchestrator, projection reconciler, terminal runtime adapter, process supervisor, and approval broker. AI and GitHub workers join later with their v1.x features.

## What the daemon owns

- All gRPC behavior. Every call goes through `AuthEnforcer`; a consequential operation atomically claims its method, target, argument, and rendered-plan-bound `HumanApproval` while creating the durable operation journal, then consumes it when that exact plan completes. Every parseable transport attempt produces exactly one SQLite audit row: in the target repo database when the repo resolves, otherwise in the user database.
- Durable creation, checkpoint, close, reopen, and repair sagas. The managed workspace's exact `@` is persisted as the live thread head; bookmarks are explicit checkpoints.
- The cascade state machine. It classifies observed jj transitions into `NativeRewrite`, `ParentAdvance`, `AlreadyAligned`, or `TopologyDiverged`; validates a strict linear owned stack; persists exact-base-transition `sync_intents`; binds a parallel-tool-batch barrier before mutation; and owns soft-batch or restart-startup delivery proof through acknowledgement.
- Projection reconciliation for workspace records, paths, bookmarks, and terminal bindings. Only unique identity-preserving normalization is automatic; ambiguous changes become named `kk repair` plans.
- The dedicated Herdr server's lifecycle and generated configuration, terminal-group provisioning and close through `TerminalRuntime`, and one-way presentation publishing. See [The dedicated Herdr server](#the-dedicated-herdr-server).
- OS process proofs through `ProcessSupervisor`: process identity, write-ahead freeze, verified resume, termination with verified exit, workspace-holder inventory, and the orphan scan. A runtime reply is never an input to these proofs except as a source of root process ids that the supervisor re-reads from the OS.
- The v1.x transcript JSONL tail. The per-(thread, session_id) offset advances atomically with `thread_messages` inserts so persisted state never diverges from inserted rows.
- Op-log watching. See [`op-log-watcher.md`](op-log-watcher.md).
- Auto-rename / auto-describe ownership and execution, when that v1.x feature ships.

## What the daemon does NOT own

- Active-thread focus. Which terminal a human is looking at belongs to each Herdr client. `kk switch` is a summary lookup in `kkd` plus a caller-local focus request made by `kk` through `TerminalClient`; it mutates no terminal, needs no `HumanApproval`, and there is no mutating `Switch` RPC. `kkd` never calls a focus method on a viewer's behalf, and there is no ambient operational Admin authority. Caller-local focus requires the Herdr extension `client_targeted_focus`, the only upstream extension kiki requires; without it `kk switch` fails naming the capability, and only the explicit `kk switch --all-clients` moves every attached client.
- The terminal. Herdr owns PTYs, panes, tabs, layout, scrollback, copy mode, input, rendering, its native sidebar, and toasts. `kkd` provisions and closes terminal groups and publishes labels and tokens through Herdr's JSON socket API; it does not multiplex, render, or read a decision back out of anything Herdr displays. `kkd` never calls Herdr's `worktree.*` methods.
- jj revisions. `jj` owns revisions; `kkd` reacts to op-log events and issues thread-aware porcelain. Users can run `jj` directly any time and `kkd` reacts to whatever it sees.

## Context discovery

"Which thread am I in?" is resolved by `ContextDiscovery`, in this order:

1. An explicit CLI target.
2. `KIKI_THREAD_ID` in the environment. Kiki sets it explicitly on every role pane; Herdr does not copy one pane's explicit environment into a split.
3. Herdr pane identity. When the caller's `HERDR_SOCKET_PATH` is kiki's dedicated server, `kk` sends the caller's `HERDR_WORKSPACE_ID`, `HERDR_TAB_ID`, and `HERDR_PANE_ID` to `kkd`. `kkd` resolves them against the bindings of the current `server_instance_id`, and accepts the result only after it verifies, from the CLI connection's peer credentials, that the calling process is a descendant or session member of that pane's root process on the current server instance. This is how a pane the user split natively resolves to its thread. Pane identity from any other Herdr server is ignored. Pane ids in an environment can go stale after a native pane move; the verification is what catches that.
4. The current working directory.

A command started from a Herdr popup or keybinding has no `HERDR_PANE_ID`; Herdr supplies `HERDR_ACTIVE_WORKSPACE_ID`, `HERDR_ACTIVE_TAB_ID`, and `HERDR_ACTIVE_PANE_ID` instead. `kkd` applies the same resolution to the active pane's terminal group, but only as a locator for read-only and navigation commands. A mutation invoked from a popup still needs the thread credential and, where required, an approval.

Environment text is a locator, not authority. Herdr ids never authorize anything and never substitute for a credential. A ref observed under the current server instance and matching a current binding may locate the caller's contextual thread; after that, the thread's own credential is what authorizes. A Herdr id that matches no current binding on the current instance resolves nothing and falls through to the next step.

## The dedicated Herdr server

`kkd` owns one named Herdr server per user. What separates it from the user's default Herdr server is a separate server process, socket, saved session, and configuration file — not a separate directory tree. `kkd` never reads or changes the default server's configuration file, saved session, or terminals.

- **Address.** The server is named by its Herdr session name (`terminal.session`, default `kiki`). Herdr has no configuration-directory flag. It keeps a named session's socket, saved state, and logs under its own directories, keyed by the session name, and it shares its plugin registry and state directory with the user's other Herdr use. `kkd` reads the socket location from that layout and checks that the longest derived socket name fits the platform's socket-path limit before starting anything.
- **Generate and validate.** Kiki's generated configuration file is `<herdr_dir>/config.toml` (`[paths] herdr_dir`, default `<user_state_dir>/herdr/`); that directory holds only this file. The file sets automatic agent resume off, onboarding off, Herdr's update, version, and manifest checks off, toast delivery to Herdr's own toasts, and sidebar rows and width sized for kiki's label. When the v1.x sidebar tokens and keybindings ship, it also declares them. Herdr's own client can rewrite this file from its settings screen, and Herdr silently loads defaults — agent resume on — when the file fails to parse. So `kkd` regenerates the file and validates it with its own parser immediately before every server start, and refuses to start the server on any diagnostic.
- **Start.** Only `kkd` starts the server. It runs `terminal.herdr_bin` with `--session <name>` and `HERDR_CONFIG_PATH=<herdr_dir>/config.toml`. Kiki does not redirect `XDG_CONFIG_HOME` or `XDG_STATE_HOME`: panes inherit the server's whole environment, so a redirected value would make jj, git, gh, and every shell in every thread read configuration from the wrong place. For the same reason `kkd` starts the server with a deliberately constructed environment — the user's login baseline of `HOME`, `USER`, `SHELL`, `PATH`, and locale — and never the environment of whichever terminal happened to invoke `kk`. Role panes add their explicit variables on top. `HERDR_CONFIG_PATH` is visible inside panes. Starting the server creates no terminal group and starts no agent.
- **Find.** `kkd` connects to the session's socket. A running server that this `kkd` installation did not start, or whose peer identity matches no open `terminal_servers` row, is unverified: `kkd` provisions nothing on it, threads bound to it read `TerminalMissing`, and replacing it is an approved plan. `kk attach` asks `kkd` to ensure the server through `EnsureTerminalServer` and then uses Herdr's connect-only client mode for the named session; it never uses a client entry point that would start a server itself.
- **Verify.** On every connection `kkd` reads the ping reply, which returns Herdr's version, its protocol number, and an object of named boolean capability flags, and checks them against the supported range it pins. An unsupported server is not used: terminal lifecycle operations fail with an actionable error, and existing threads keep their recorded state. The adapter derives `RuntimeCapabilities` from the version and protocol plus those flags. `client_targeted_focus` must arrive as a new upstream flag. Herdr already reports `live_handoff` as true; that flag is not a gate signal, and kiki does not treat handoff as supported because of it. Herdr ignores unknown request parameters, so `kkd` never probes for an extension by sending it.
- **Identify.** `kkd` reads the socket peer's process identity `(pid, start_time)` from the OS on every connection. The `server_instance_id` is kiki's row id for one such observed peer. Herdr's public API reports no instance identity. Every recorded Herdr workspace, tab, and pane id is stored with the instance it was read under and is meaningless under any other. A pane's root process is trusted only if its parent is the current server process.
- **Observe.** `kkd` subscribes to events and then takes a snapshot. Events are wake-up hints; the snapshot is the observation. Herdr's session snapshot carries no process ids, so a snapshot is the session snapshot plus a per-pane process query. It is not atomic, and every pid in it is re-read from the OS before it is trusted.
- **Publish.** `kkd` publishes a label, and in v1.x tokens, only to a terminal group with a current binding. A remnant container left by a restore keeps whatever label Herdr restored and receives no kiki tokens. The sidebar that shows the label can be hidden or collapsed by the user; nothing depends on it being visible.

### Runtime reconciliation

`kkd` resubscribes, takes a fresh snapshot, reconciles every terminal binding, and republishes presentation after each of these: daemon start, a reconnect, any connection error, a reported loss of events, and a changed `server_instance_id`. Reconciliation compares each binding's recorded handles and launcher process identities with the snapshot and with the OS. A terminal change that an in-flight lifecycle journal expected belongs to that journal. Every other difference becomes a projection issue under the rules in [Threads](../03-threads.md#projection-divergence-and-repair). Nothing is reconstructed from Herdr's event history, labels, or tokens.

### Orphan scan

A process can outlive its pane, its terminal group, and the terminal server. `kkd` asks `ProcessSupervisor` which recorded process identities are still alive:

- at daemon start, before any thread is reported `Active`;
- whenever the `server_instance_id` changes;
- before provisioning a replacement terminal group or activating a replacement incarnation's gate.

`OrphanedProcess` is a standing projection issue with exactly two causes:

- a **recorded** process identity that is alive without a current binding;
- a **harness remnant**: before a replacement incarnation's gate is activated, an inventory rooted at the `agent` launcher must show no process other than the launcher itself in its descendant, session, and process-group sets. A surviving tool child of the retired harness is a remnant.

While the issue is unresolved, `kkd` activates no gate and materializes nothing in that workspace. Recorded role processes that are pane members on the current instance are terminal members, not orphans.

An **unrecorded** same-UID process that holds the workspace is not a standing issue and never blocks an `Active` thread's boundaries. It matters only to an operation that deletes the workspace: close, destroy, `close-without-terminal`, and failed-create cleanup. There it makes the result `Unknown`, unless the approved plan names that exact holder identity as accepted — the human's informed choice, such as an editor left open. A holder the plan does not name is drift. The holder scan excludes `kkd`, its own child processes, and the invoking `kk` process. Every `Unknown` result reports each offending pid, its command line, and the step that clears it. Processes running as another user are invisible to the scan; kiki says so and claims nothing about them. A member that is stopped by a debugger makes the result `Unknown`.

`kkd` terminates only identities it recorded, and only after it has stopped them and re-read their identity: on a mismatch it continues that process and treats it as unknown. Where the OS offers a process handle, such as a pidfd, `kkd` signals through the handle rather than a bare pid.

## Op attribution

jj offers no way to set an operation's description from the command line. `kkd` attributes its own operations in two ways: every jj invocation runs with a per-invocation operation user and host configuration that marks it as kiki's, and `kkd` records every operation id the command wrote in `op_attribution` — one command may write several. Classification still runs on every operation, kiki's own included; attribution suppresses only cascade re-triggering. The initiating reconciliation handler compares the before/result operation views and records `NativeRewrite` intents for any other workspaces jj evolved.

## Failure model

- On daemon crash, in-flight gRPC calls fail; clients reconnect. Cascade crash safety comes from durable intent and barrier state plus post-stdout `MarkDelivered(intent_id, incarnation_id, model_turn_id, tool_batch_id)` ordering, not from the daemon staying up.
- On daemon restart, op-log catch-up walks every unprocessed operation reachable from the observed frontier through normalized parent edges, in topological order. It runs _before_ JSONL backfill so anchor lookups see current operation and workspace history.
- `kkd` runs under launchd or systemd-user and is restarted by it. Restart recovery reads sqlite state; thread identity and persisted lifecycle state survive reboots.
- **`kkd` crashes during a freeze.** Each discovered process identity was committed to `process_records`, with its prior stop state and the freeze's lifecycle operation id, before it was signalled. On restart `kkd` rebuilds the frozen set from those rows. Before the final proof it performs verified resume. After the final proof it continues the journal forward. The filesystem watch died with the old process, so the post-exit filesystem recheck re-reads the generation and fingerprint and compares them with the final proof's journaled values; a mismatch is `CloseFailed` or `DestroyFailed` with files preserved.
- **`kkd` restarts while the Herdr server survives.** Agents keep running. `kkd` reconnects, verifies the peer's `(pid, start_time)` against its open `terminal_servers` row, snapshots, runs the orphan scan, and reconciles. `agent` launchers reopen their supervision streams. A binding whose recorded launcher and harness process identities are still live under the same instance continues, and the harness's next hook round-trip re-proves the incarnation as usual. A live launcher whose harness is gone keeps its binding and its `agent` role: the incarnation is retired without acknowledgement, `AgentStatus` is `Crashed`, and the thread's lifecycle is unchanged. A binding whose `agent` launcher is gone ends, and its thread raises `TerminalMissing`.
- **The harness exits while its launcher lives.** The launcher reports the exit, re-reads the thread credential, and awaits the next gate. The incarnation is retired without acknowledgement and the thread shows `blocked`, never working. A replacement incarnation is a new `agent_sessions` row and a new one-use gate awaited by the same accepted launcher. It needs no terminal provisioning. Its gate is activated only after the harness-remnant check above passes. Two paths start one: kiki's own protocol restarts — a cascade hard restart or `RestartStartup` replacement — which are daemon-initiated steps of the delivery protocol and need no `HumanApproval`; and the `kk repair` plan `restart-agent`, the explicit restart path, which is same-thread and needs no approval in thread context. `restart-agent` uses `RestartStartup` when an intent is pending. Only the launcher's own exit, or the loss of its binding or server instance, ends the `agent` role and raises `TerminalMissing`, whose restart plan needs approval. In a group whose only pane is the `agent` pane, the launcher's exit also removes the whole Herdr workspace, because Herdr drops a workspace when its last pane's command exits and reports only a pane-exit event.
- **The Herdr server crashes or is killed.** Its PTYs close. Processes that ignored hangup or left their session can survive and are absent from every terminal view. `kkd` observes the connection error, treats every binding of that instance as ended, retires every incarnation without acknowledgement, and runs the orphan scan before anything else. `kkd` may start a fresh server so that `kk attach` and repair work, but it starts no agent on its own: each affected thread raises `TerminalMissing`. A terminal restart is an approved `kk repair` plan with a fresh credential, launch settings, gate, and handshake. It never reuses a remnant or unbound container. The plan lists every remnant or unbound container whose processes hold the workspace, with those processes; closes each through freeze, termination with verified exit, and a close request; re-runs the holder scan; and only then provisions a fresh terminal group. An unresolved `OrphanedProcess` blocks that plan for its workspace.
- **Cold restore.** A restarted server restores layout, labels, working directories, and the same public ids, with new processes. Launch argv is saved but not rerun; launch environment and tokens are not kept. A restored pane whose saved directory is gone has no process at all. Herdr allocates workspace ids from a counter that resumes above the highest surviving id, so an id may recur for an unrelated new group. A restored pane is a plain shell with no role, running in the jj workspace. `kkd` handles a cold restore exactly as a server crash: new instance, ended bindings, orphan scan, `TerminalMissing`, and the same restart plan that closes remnant containers before provisioning. A restored pane is never `Active` evidence, and the generated configuration keeps Herdr from resuming agents itself.
- **Live handoff** is unsupported in v1 and `kkd` never initiates it. An observed instance change with surviving recorded processes blocks boundary mutation and raises `TerminalMissing` with that evidence.
- **A runtime call's reply is lost.** `kkd` never repeats a create or close blindly. Provisioning recovers from a fresh snapshot and launcher reports, and rotates the provision nonce before any re-issued create call. Close does not wait on the reply at all: kiki has already terminated the frozen set with verified exit, and the close request is cleanup. See [Provisioning](terminal-runtime.md#provisioning) and [Process supervision](terminal-runtime.md#process-supervision).
- **Creation or reopen fails after provisioning.** Automatic compensation may close the provisioned group and remove the new jj workspace only while the launch gate was never activated, `ProcessSupervisor` shows the group contains nothing but kiki's own blocked launchers, and the workspace still equals its initial materialization. Otherwise the saga stops with its projections intact, and cleanup is an approved repair plan that uses the close machinery.
- Before a batch has activated a cascade barrier, `kk-hook` may degrade to a cached batch-wide pass-through when `kkd` is unreachable and log the gap under `errors/<thread_id>.log`. If restart loses that cache and the in-flight batch is unknown, kiki leaves files untouched and replaces the incarnation to establish a clean boundary. Once reconciliation may have changed files, the durable barrier fails closed: every sibling call remains blocked, and an unprovable batch-completion boundary forces hard restart with the saved payload. Missed transitions remain reconstructable from jj's operation DAG, and the next successful boundary probes actual files before mutation. See [Harness adapter](harness-adapter.md).
- A same-UID adversary can read credentials and invoke `kk` directly. The daemon's authorization model reduces accidental and buggy agent blast radius; it does not defend against active malice — see [Authority](../04-authority.md).
