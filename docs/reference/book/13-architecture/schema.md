# State schema

kiki state lives in two SQLite databases. All tables are versioned via migrations. Recovery on daemon restart reads from sqlite; threads survive crashes and reboots.

## Database split

| Path                                      | Scope    | Contents                                                                                  |
| ----------------------------------------- | -------- | ----------------------------------------------------------------------------------------- |
| `~/.config/kiki/state.db`                 | per-user | repo registry, daemon meta, terminal server instances, presenters, unscoped audit         |
| `~/.config/kiki/repos/<repo_id>/state.db` | per-repo | threads, terminal bindings, process records, agent sessions, transcripts, cascades, audit |

Both databases live under `~/.config/kiki/` — kiki's centralized state directory. The source repo's own filesystem holds no kiki state; the per-repo `state.db` lives at `~/.config/kiki/repos/<repo_id>/state.db`, where `<repo_id>` is a UUID assigned at `kk init` and recorded in the per-user `repos` table. The user-level database knows which repos kkd watches; the per-repo database holds everything that lives or dies with the repo.

The `<repo_id>` UUID gives the centralized directory a stable, opaque name during one registration; it is **not** an identity that survives the source repo being moved out of band. With no breadcrumb inside the source repo, kiki's only handle on a registered repo is its `canonical_path`. If the user `mv`s the tree, `kk` invoked from the new location reports the repo as unregistered (because no `canonical_path` matches). The prior `<repo_id>` and its centralized state remain in `~/.config/kiki/repos/<old_repo_id>/` until `kk repo unregister` is run against the original path. The v1 recoveries are: move the source tree back so the registered `canonical_path` matches; or `kk repo unregister` followed by `kk init` at the new location, which starts a fresh registration with a new `repo_id`. By default, `kk repo unregister` removes both the registry row and the centralized state directory; `--keep-state` retains the directory on disk for manual inspection but offers no kiki-managed recovery — a subsequent `kk init` at the same canonical path mints a fresh `<repo_id>` with no link to the preserved bytes. See [Commands · Repo registry](../09-commands.md#repo-registry). A move-aware `kk repo relocate` command is not in v1.

## Tables

The list below is table-level. Column-level definitions are derived from the behavioral chapters.

### Per-user (`~/.config/kiki/state.db`)

- `repos` — `(repo_id, canonical_path, registered_at, opt_in_metadata)`. `repo_id` is a UUID assigned at `kk init` and keys the per-repo state directory at `~/.config/kiki/repos/<repo_id>/`. `canonical_path` is the realpath of the registered source repo at registration time and is the only handle kiki has for matching a future invocation back to this row. `repo_id` is stable for the life of the registration (so the centralized directory's name does not churn while kkd is running); it is **not** preserved across `kk repo unregister` + `kk init`, which is a fresh registration with a new UUID. An out-of-band `mv` of the source tree cannot be auto-detected — see the move semantics in the section above.
- `daemon_meta` — daemon startup info, last-known socket path, schema version.
- `terminal_servers` — one row per observed lifetime of the dedicated terminal server; `server_instance_id` is kiki's own row id for one observed socket peer `(pid, start_time)`, not a value the runtime supplies. Columns: `(server_instance_id, runtime_kind, session_name, socket_path, peer_pid, peer_start_time, runtime_version, protocol, capabilities_json, first_seen_at, ended_at?)`. The server is per-user, so the row lives here and per-repo rows name it by `server_instance_id`. Identity is the socket peer's `(peer_pid, peer_start_time)`, verified on every connection; a session name, a socket path, or a version string is never identity. `runtime_version`, `protocol`, and `capabilities_json` are the values reported at that instance's start and are what `RuntimeCapabilities` was derived from. A peer whose identity differs from the open row ends that row and inserts a new one. The `TerminalRuntime`, `TerminalClient`, and `ProcessSupervisor` traits are defined in `kiki-core`; `HerdrRuntime` is the Herdr adapter, and `runtime_kind` names the adapter that observed the row. See [Terminal runtime](terminal-runtime.md#identity).
- `approval_presenters` — foreground-channel enrollments `(presenter_id, frontend_kind, credential_hash, channel_binding, enrolled_at, last_seen_at, revoked_at?)`. Enrollment requires bootstrap Admin, but enrollment is not approval for an operation. A presenter proves that a confirmation came from a registered interactive CLI or TUI channel; it cannot mint a capability without completing a persisted challenge.
- `user_approval_challenges` and `user_human_approvals` — the same two-phase challenge and one-use-capability records described below, for operations with no repository target. Repository-scoped confirmations are stored only in the target repository database.
- `user_approved_operations` and `user_approved_operation_steps` — durable claim envelopes and idempotent step journals for approved operations whose authority must survive without a repo database, including registration and unregister. Their shape matches the per-repo tables below; unregister completes its user-level journal only after the target repo state is deleted.
- `user_audit_log` — append-only attempts that have no valid repository target, including bootstrap, `ListRepos`, registration, malformed repo selectors, and authorization failures before a repo can be resolved. Its row shape matches per-repo `audit_log` and permits null credential, approval, and presenter identities.

### Per-repo (`~/.config/kiki/repos/<repo_id>/state.db`)

- `threads` — per-thread row carrying stable identity; bookmark name, workspace, current terminal binding, and harness projection references; `thread_head_commit_id`; the checkpoint fields `checkpoint_commit_id`, `checkpoint_change_id`, `checkpoint_op_id`, `bookmark_expected_commit_id`, and `bookmark_expected_op_id`; `owned_stack_base_commit_id`; and a `lifecycle` column with values `Creating | Active | CreateFailed | ClosePreflight | CloseCommit | CloseFailed | Closed | ProjectionDiverged | DestroyCommit | DestroyFailed | Destroyed` (see [Threads](../03-threads.md)). `projection_resume_lifecycle` is null except in `ProjectionDiverged`, where it records whether successful repair must restore `Active` or `Closed` invariants. For an active coherent thread, the managed workspace's exact `@` is the live head and `thread_head_commit_id` is its last-observed exact value. `checkpoint_commit_id`, with `checkpoint_change_id` and `checkpoint_op_id`, records the latest explicit placement: the exact commit, change, and operation where kiki last put the bookmark. It changes only when a journaled checkpoint places the bookmark. The placed commit follows the checkpoint target rule: the live head, or its parent when the head is an empty, undescribed working-copy commit whose parent is on the owned chain. `bookmark_expected_commit_id` is the expected bookmark target used by the projection audit, publish, and reopen, and `bookmark_expected_op_id` is the operation that established it. It starts equal to the placement and afterwards changes only through a recorded succession; it never changes because `@` moved. The checkpoint relationship `current | behind | ahead | diverged` is derived from it and the live head on a single-parent path and is not stored: `current` when they are equal or the head is an empty, undescribed working-copy commit whose parent is the expected target; `behind` when the head is any other descendant of the expected target; `ahead` when the head is an ancestor of it; `diverged` otherwise. The bookmark name is a projection reference, not identity: a proven external rename replaces it in place under the rename rule in [Op-log watcher](op-log-watcher.md#the-classifier), and each such change is appended to `thread_bookmark_renames`. The current terminal binding reference names at most one non-`Ended` `terminal_bindings` row; a Herdr ref, label, or path stored anywhere else is a locator or a hint, never the binding. `owned_stack_base_commit_id` survives follows-edge deletion and advances only with a completed reconciliation, so detach and later destroy validation retain an exact structural base. Cascade progress is not projected onto this row; it is derived from `sync_intents`.
- `thread_links` — directed follows edges, DAG-validated at insert time, including `last_synchronized_parent_commit_id`. The initial parent anchor comes from the parent's exact live head in a pinned, revalidated operation view, never its bookmark or a stale cache. Immediately before explicit rebase, every commit after the thread's exact owned-stack base through its exact live head must form one strict single-parent chain and be owned by that child. Merge commits, multiple roots, conflicts, or foreign commits produce `TopologyDiverged`; kiki never infers a broader source revset or trusts a remembered “root” identity in place of validating the path.
- `thread_checkpoints` — append-only placement history `(checkpoint_id, thread_id, seq, lifecycle_op_id, reason: Creation | Publish | Close | Detach | RepairRestore | RepairAdopt, placed_change_id, placed_commit_id, placed_op_id, placed_at)` with `UNIQUE (thread_id, seq)`. One row is appended by every explicit placement — creation, publish, close, detach, and every applied bookmark repair plan — in the transaction that verifies the bookmark's resulting target and operation. `RepairRestore` places the bookmark at the expected target (`bookmark_expected_commit_id`), never at an older placed commit; `RepairAdopt` places it at the chosen exact commit. A checkpoint placement (`Creation | Publish | Close | Detach`) is refused unless the placed commit equals or descends from the expected target. A backward or sideways placement happens only through an approved `adopt-bookmark` or `choose-bookmark-target` repair plan, recorded as `RepairAdopt` with that plan's `lifecycle_op_id`. `RepairRestore` is refused while the expected target is hidden. Placements are scoped by operation ancestry exactly like successions: a placement applies to an operation view only when `placed_op_id` is that view's operation or an ancestor of it, because a pinned placement can land beside a concurrent operation. Rows are never updated or deleted while the thread exists; a later rewrite of the placed commit does not change them.
- `thread_checkpoint_successions` — append-only native successor tracking `(checkpoint_id, seq, kind: SameChange | PredecessorOtherChange | Reverted, from_commit_id, to_commit_id, to_change_id, op_id, evidence_op_id?, evidence_commit_id?, observed_at)` with `UNIQUE (checkpoint_id, seq)` and `UNIQUE (checkpoint_id, op_id)`. A row records that jj itself carried the bookmark from `from_commit_id` to `to_commit_id` in operation `op_id`, under the classifier in [Op-log watcher](op-log-watcher.md#checkpoint-tracking). `SameChange` and `PredecessorOtherChange` are proved by an operation predecessor record; `evidence_op_id` names the operation whose record was used when it is not `op_id`, and `evidence_commit_id` names the commit that recorded the predecessor when it is not `to_commit_id` (a squash into a commit other than the parent). `Reverted` records an undo: `to_commit_id` is the placed commit or an earlier row's `to_commit_id` of the same placement, and it needs no predecessor record. Rows are written for kiki's own operations as well as external ones. Rows attach to the placement they succeed. The expected target in any operation view is the latest placement applicable to that view, updated by its rows whose `op_id` is an ancestor of that view; `threads.bookmark_expected_commit_id` caches that value for the agreed frontier.
- `thread_bookmark_renames` — append-only normalization journal `(rename_id, thread_id, from_name, to_name, op_id, target_commit_id, observed_at)` with `UNIQUE (thread_id, op_id)`. A row records that one exact operation removed the thread's bookmark name and created exactly one new local name on the expected target, that the operation changed no remote or `@git` bookmark and was not an import or fetch, and that kiki adopted the new name. It is written in the transaction that updates the thread row's bookmark name. It appends no placement and no succession by itself.
- `thread_lifecycle_ops` — durable creation, close, reopen, checkpoint, repair, and later destroy sagas. Each row carries `(lifecycle_op_id, thread_id, kind, state, started_at, updated_at, completed_at?, last_error?, context_json)`. `context_json` contains pinned ids and fingerprints needed to retry but is not a substitute for normalized thread or step state. For a plan that deletes a workspace — close, destroy, `close-without-terminal`, and failed-create cleanup — it also holds the approved plan's accepted workspace-holder identities, each an exact `(pid, start_time)` with its command line, and the remnant or unbound terminal containers the plan lists with their processes. A holder the plan does not name is drift.
- `thread_lifecycle_steps` — append/update journal keyed by `(lifecycle_op_id, ordinal)` carrying `(name, state: Pending | Started | Completed | Compensating | Compensated | Failed, attempt, started_at?, completed_at?, input_fingerprint?, result_json?, error?)`. A step is marked `Started` before its external side effect and records the stable external identity required to detect already-completed work. Creation and reopen compensation run completed steps in reverse order. Close records, in this order and separately: freeze, post-freeze recheck, checkpoint, each child reconcile/checkpoint/detach, final proof, termination of the frozen set with verified exit, the terminal-group close request, post-exit filesystem recheck, workspace forget, and directory delete. The freeze is write-ahead: each discovered identity is committed to `process_records` with its prior stop state and this operation's id before it is signalled, so a crash mid-freeze is recovered from those rows by verified resume. The post-freeze recheck runs immediately after the freeze, binds to the approved fingerprint, shows that no frozen member holds an open descriptor under the repository's `.jj` directory, and precedes the checkpoint. The final proof runs after the checkpoint and all child work; it re-asserts that every member is stopped and repeats process membership, holders, the runtime pane set, the filesystem generation, and the fingerprint, and it journals the generation and fingerprint it saw. It is the recovery boundary. Kiki then terminates the frozen set itself, while it is still stopped and before the runtime is asked to close anything: per identity it confirms the process is still stopped and still the recorded `(pid, start_time)`, kills it, and verifies it gone. The terminal-group close request is cleanup only, and its reply is not evidence. The post-exit filesystem recheck requires the generation and fingerprint to equal the final proof's journaled values, and it is re-read after any `kkd` crash because the watch does not survive one; any mismatch is `CloseFailed` with files preserved. Every step taken while frozen has a deadline, and expiry takes verified resume. Child work completes while the parent remains frozen. A pre-irreversible abort of a `close-without-terminal` plan returns `CloseCommit` to `ProjectionDiverged`. Destroy records, in this order and separately: freeze, post-freeze recheck, final proof, termination of the frozen set with verified exit, the terminal-group close request, post-exit filesystem recheck, bookmark deletion, optional exact revision abandonment, workspace forget and directory delete, credential revocation, and tombstoning. Drift before termination takes verified resume. Process termination is destroy's first irreversible step; after it only `DestroyFailed` or finishing the plan applies, so failure after an irreversible step cannot masquerade as an intact lifecycle.
- `thread_projection_issues` — repair ledger `(issue_id, thread_id, kind, expected_json, observed_json, detected_at, notified_at?, resolved_at?, resolution?)`. Kinds include `WorkspaceDirectoryMissing | WorkspaceRecordMissing | WorkspacePathMismatch | BookmarkMissing | BookmarkMoved | BookmarkConflicted | TerminalMissing | OrphanedProcess`. A bookmark issue's `expected_json` carries the expected target with its placement and latest succession; `observed_json` carries the observed target set, the conflict flag, the exact operation, whether the expected target is hidden, and whatever predecessor evidence exists. `BookmarkMissing` with the expected target hidden carries the evidence `CheckpointAbandoned`. A bookmark issue is resolved without a plan when a later operation shows the bookmark unconflicted on the expected target; `resolution` then records that operation. `TerminalMissing` records the ended binding and the observed cause; `OrphanedProcess` records the recorded process identities found alive without a current binding, or a harness remnant: the processes other than the launcher found in the `agent` launcher's descendant, session, or process-group set after its harness was retired. An unrecorded same-UID workspace holder is not an `OrphanedProcess` and is not stored as an issue. An unresolved issue places an otherwise coherent active or closed thread in `ProjectionDiverged`, except for a temporary mismatch owned by an in-progress lifecycle journal. Issue effects are derived from `kind`: bookmark-only issues (`BookmarkMissing`, `BookmarkMoved`, `BookmarkConflicted`) block checkpoint, publish, close, and detach, and freeze native successor tracking for that thread, but not unambiguous workspace-head observation or follows classification; `TerminalMissing` permits head observation but blocks boundary delivery, workspace materialization, and lifecycle mutation other than an approved restart, `close-without-terminal`, or destroy plan; `OrphanedProcess` permits head observation but blocks activating a replacement incarnation's launch gate, workspace materialization, and workspace forget or deletion; workspace identity or path ambiguity blocks both. Only identity-preserving, unique normalization may resolve automatically. A proven bookmark rename is such a normalization and raises no issue. Adopt, recreate, move, restart, and terminate choices require a recorded `kk repair` resolution. A recorded native succession is not a resolution and raises no issue.
- `repo_issues` — repo-level repair ledger `(issue_id, kind: OperationHistoryRewritten, expected_json, observed_json, detected_at, notified_at?, resolved_at?, resolution?)`. `OperationHistoryRewritten` is raised once per repo when no frontier head descends from any recorded operation and at least one thread's observed bookmark or workspace `@` differs from its cached value; `observed_json` lists those threads. It replaces per-thread bookmark issues for that gap. While it is unresolved, checkpoint, publish, close, detach, and explicit rebase are blocked for the listed threads.
- `terminal_bindings` — one row per provisioned terminal group for one thread on one server instance `(terminal_binding_id, thread_id, server_instance_id, provision_id UNIQUE, provision_nonce_hash, lifecycle_op_id, group_ref, state: Provisioning | Bound | Ended, ended_reason?, created_at, ended_at?)`. `provision_id` is persisted before the runtime is asked to create anything and is what a pane launcher's report names, so a lost reply or a duplicate group resolves to one accepted binding. `provision_nonce_hash` is the hash of the provision nonce. There is one nonce per provision. It reaches each role launcher through its launch environment and never through argv, because the runtime saves launch argv; argv carries only `provision_id` and the role. The nonce itself is never stored. Before any re-issued create call for the same provision, the nonce is rotated and the hash replaced, so a launcher from the earlier call cannot claim. A launcher report authenticates with the thread-scoped credential plus that nonce, and `kkd` reads the launcher's process identity from the OS through the socket's peer credentials instead of trusting a reported one. `group_ref` is the Herdr workspace ref; it is meaningful only together with `server_instance_id`. The first accepted launcher fixes it: a launcher that reports the same `provision_id` from another Herdr workspace is refused. A report is accepted only when the caller's OS identity has the current server instance's process as its parent and a fresh per-pane process query shows the reported pane's root process is that caller. Two transactions are kept apart. The first accepts exactly one launcher for `(provision_id, role)`, records its OS-read process identity, and marks the binding `Bound`. The second records a new incarnation and activates its launch gate, and it requires a `Bound` binding. `Bound` is entered only by the first. A binding is `Ended` when it is closed, replaced, or its server instance ends, and an ended binding is never revived.
- `terminal_panes` — role panes of a binding `(terminal_binding_id, role: agent | shell | ui, tab_ref, pane_ref, terminal_ref?, launcher_pid, launcher_start_time, nonce_consumed_at, claimed_at, ended_at?)`. A row exists only because a pane launcher claimed `(provision_id, role)` through the gate; pane position, label, and title never assign a role. `nonce_consumed_at` records that this role's claim consumed the provision nonce: the nonce admits one claim per `(terminal_binding_id, role)`, and a second presentation for a consumed role is refused. `launcher_pid` and `launcher_start_time` are the claiming process identity as read from peer credentials, and the role is bound to that identity. It survives a `shell` or `ui` launcher replacing itself with the shell or UI program, because replacement keeps `(pid, start_time)`. The role ends when that process identity ends, and `kkd` observes that end from the OS; it is not reported. They are a different fact from the harness process identity on `agent_sessions`: the `agent` launcher stays alive as the harness's parent, so both identities are live at once. `terminal_ref` holds Herdr's `terminal_id` and is a change hint only. `user` is not a role; it is the absence of one, so `user` panes are observed in runtime snapshots and never stored here.
- `process_records` — the OS process identities kiki recorded for a thread `(record_id, thread_id, terminal_binding_id?, agent_session_id?, pid, start_time, os_session_id, process_group_id, source: Launcher | Harness | HarnessTree | FreezeDiscovery, recorded_at, prior_stop_state?, freeze_lifecycle_op_id?, exit_verified_at?)`. These are the identities the orphan scan looks for and the identities verified exit checks. A process is the recorded one only when both `pid` and `start_time` match. `HarnessTree` rows are the harness's descendants recorded when kiki terminates or hard-pauses a harness, which covers its whole process tree. `prior_stop_state` and `freeze_lifecycle_op_id` are set for members of a frozen set, and the row is committed before the process is signalled, so the frozen set is reconstructible from rows and verified resume restores exactly the prior states. `exit_verified_at` is written only by `ProcessSupervisor` after it observed that exact identity gone; a runtime reply never sets it. Kiki signals only identities present in this table, and terminates one only after it is stopped and its identity re-read.
- `agent_sessions` — one row per runtime process incarnation carrying `(agent_session_id, thread_id, harness_session_id, terminal_binding_id, launcher_pid, launcher_start_time, harness_pid?, harness_start_time?, started_at, retired_at?, launch_gate_id?, gate_activated_at?, harness_started_at?, ready_fingerprint?, exclusive_hook_fingerprint?, exclusive_hook_proven_at?, delivered_intent_id?, startup_intent_id?, startup_intent_epoch?, startup_delivery_id?, startup_payload_sha256?, startup_proven_at?)`. `agent_session_id` changes on every process start even when `--resume` reuses `harness_session_id`; every incarnation must independently prove exclusive hook control before it is ready or may mutate a managed workspace. The incarnation belongs to the `agent` role pane of `terminal_binding_id`. The launcher identity is copied from the binding's live `agent` row in `terminal_panes`; the harness identity is recorded by `ReportHarnessStarted`: the launcher creates the harness child held before it runs, reports the child's pid, `kkd` verifies from the OS that the process is that launcher's child and records `(harness_pid, harness_start_time)`, and only then does the launcher release it. The harness identity is therefore recorded before the harness runs; the ready handshake records readiness, not the pid. `kkd` resolves the launch specification through the harness adapter and the pane launcher only executes it. A hard-pause retires the incarnation by terminating the harness process tree through `ProcessSupervisor`, leaving the launcher alive. The `agent` launcher outlives incarnations. Each incarnation has its own one-use `launch_gate_id`, and the same accepted launcher awaits successive gates: "one-use" describes a gate, not the launcher. When the harness exits, the launcher reports the child's exit status and awaits the next gate; the incarnation is retired without acknowledgement, the `agent` role and the binding stay live, and the thread's lifecycle is unchanged. A replacement incarnation is a new row and a new gate on that launcher, with no terminal provisioning. Its gate is activated only after an inventory rooted at the `agent` launcher shows no process other than the launcher itself; a survivor is an `OrphanedProcess` harness remnant and blocks the gate. The thread credential's file path is stable and its contents are replaced atomically when an incarnation ends and at reopen or terminal restart; the launcher re-reads it after reporting the harness exit. During creation, a launcher blocks on `launch_gate_id`; activation authorizes the harness start but leaves the thread `Creating`. A validated ready handshake records the harness and hook fingerprints, and only that transaction completes the saga and enters `Active`. Delivery pointers name a synthetic result awaiting acknowledgement either through a soft batch barrier or as the byte-stable, one-use-tagged first startup message of a replacement process.
- `metadata_writes` — kk-ownership content-hash ledger for descriptions and bookmark names.
- `sync_intents` — the sole durable reconciliation, embedded-outbox, and delivery authority. Each row carries `(intent_id, thread_id, seq, kind, from_base_commit_id, to_base_commit_id, classification_op_id, state, planned_op_id?, result_op_id?, result_workspace_commit_id?, payload?, anchor_change_id?, anchor_commit_id?, anchor_op_id?, prepared_at?, delivery_mode?, delivered_at?, acknowledged_at?, transcript_row_id?, barrier_incarnation_id?, barrier_model_turn_id?, barrier_tool_batch_id?, barrier_bound_at?, batch_completed_at?, soft_redelivery_count, restart_incarnation_id?, restart_startup_delivery_id?, restart_startup_proven_at?, delivery_exhausted_at?, delivery_epoch, delivery_rearmed_at?, recovery_reason?, recovery_bundle_path?, recovery_fingerprint?, recovery_details?, result_has_conflicts, conflicts_cleared_op_id?)`, where kind is `NativeRewrite | ParentAdvance`, `delivery_mode` is `SoftBatch | RestartStartup`, and state is `Detected | Reconciling | Materialized | Delivered | Acknowledged | RecoveryRequired | TopologyDiverged | Superseded`. `result_has_conflicts` (default false) records that the reconciliation result contains jj conflicts; it is a flag, not a state, and `conflicts_cleared_op_id` names the operation whose view first showed the thread's chain conflict-free. Soft-barrier and restart-startup proof fields are embedded on the intent rather than stored in another progress table. Delivery-attempt bounds are durable on the same row: `soft_redelivery_count` (default 0) counts barrier rebinds after contrary delivery receipts, replacement attempts are counted from the persisted `agent_sessions` rows whose `(startup_intent_id, startup_intent_epoch)` match the intent and its current `delivery_epoch`, and `delivery_exhausted_at` freezes the intent for human attention. `UNIQUE (thread_id, seq)` orders intents; sequence allocation and insertion occur in one transaction. Recovery bundles live under `~/.config/kiki/repos/<repo_id>/recovery/<intent_id>/`, outside the source workspace. The runtime lock remains an in-memory `tokio::sync::Mutex` keyed by `thread_id`; restart recovery resumes from intent state, exact operation ids, and durable delivery proof. See [Cascade](../05-cascade.md) and the [embedded-outbox design note](../17-decisions/cascade-outbox.md).
- `sync_intent_triggers` — normalized `(intent_id, op_id)` rows with `UNIQUE (intent_id, op_id)`. Coalescing adds observed operation ids here and updates `classification_op_id` to the exact view used for reclassification only while the intent remains pre-materialization; it does not impose a false linear “through” order on jj's operation DAG.
- `op_attribution` — every operation id a kiki-run jj command wrote `(op_id, invocation_id, kind, lifecycle_op_id?, intent_id?, recorded_at)`. One command may write several operations, and each gets a row under the same `invocation_id`. Attribution is by recorded id and by the per-invocation operation user and host jj stores on the operation; kiki sets no operation description. It suppresses only cascade re-triggering: every attributed operation is still classified for workspace heads and checkpoint tracking. Kind `Integration` marks a deliberate merge of operation heads.
- `op_history` — operation-node cache `(repo_id, op_id, committed_at, observed_at, processed_at?)` with `UNIQUE (repo_id, op_id)`. A row is processed only after every relevant workspace transition for that node has been classified durably.
- `op_history_anchors` — re-anchoring records `(repo_id, anchor_id, head_op_ids_json, reason: Silent | Repair, repo_issue_id?, recorded_at)`. A row is written when no frontier head descends from any recorded operation. Placements and successions recorded before an anchor are evaluated through the cached expected targets as of that anchor; operation ancestry is computed only from the anchor forward.
- `op_history_parents` — normalized operation-DAG edges `(repo_id, op_id, parent_op_id)` with `UNIQUE (repo_id, op_id, parent_op_id)`. No code path may collapse an operation with multiple parents to one cursor predecessor.
- `op_workspace_heads` — per-view workspace projection `(repo_id, op_id, workspace_id, change_id, commit_id)` with `UNIQUE (repo_id, op_id, workspace_id)`. The workspace key is load-bearing because `@` is workspace-local.
- `op_watch_frontier` — the current known set of operation heads `(repo_id, op_id, observed_at)` with `UNIQUE (repo_id, op_id)`. Restart catch-up walks every not-yet-processed ancestor reachable from this frontier in topological order; it is not a singular “last cursor to head” scan.
- `pr_links` — thread → PR.
- `thread_config` — per-thread config layer key/value/updated_at.
- `credentials` — `(cred_id, kind: 'Admin' | 'ThreadScoped' | 'RegistrationScoped', thread_id?, repo_id?, issued_at, revoked_at?)`. Admin is accepted only by bootstrap and approval-presenter enrollment endpoints; operational calls cannot substitute it for human approval.
- `approval_challenges` — pending foreground confirmations `(challenge_id, requester_cred_id, presenter_id?, method, repo_id, thread_id?, args_digest, rendered_plan, nonce, created_at, expires_at, confirmed_at?, confirmed_foreground_tty?, cancelled_at?)`. `BeginApproval` persists the exact plan before returning it for display. Only an enrolled foreground presenter may bind itself and confirm the nonce and digest; presenter binding, confirmation evidence, and capability issuance occur in one target-database transaction.
- `human_approvals` — one-use capabilities `(approval_id, challenge_id, requesting_cred_id, approving_presenter_id, method, repo_id?, thread_id?, args_digest, issued_at, expires_at, claimed_at?, operation_id?, consumed_at?, consuming_audit_id?)`. Claim and creation of the exact `approved_operations` envelope occur atomically before external effects. A claimed approval can resume only that operation id and cannot authorize another plan; completion marks it consumed. Expired, replayed, method-mismatched, target-mismatched, argument-drifted, unconfirmed, or channel-mismatched approvals fail closed.
- `approved_operations` — generic approval-claim envelope `(operation_id, approval_id UNIQUE, kind, thread_id?, plan_digest, state: Claimed | Running | Completed | Failed | OutcomeUnknown, claimed_at, updated_at, completed_at?, result_digest?, last_error?)`. Lifecycle operations link their envelope to `thread_lifecycle_ops`; publish, parent-merge remote updates, sensitive snapshots, and other consequential methods use this envelope directly. One approval creates one immutable envelope, and recovery may resume only its stored plan.
- `approved_operation_steps` — idempotent external-effect journal `(operation_id, ordinal, name, state, input_fingerprint, result_json?, error?)`, unique by `(operation_id, ordinal)`. Remote push and PR-base mutation are separate steps; an unknown remote result becomes `OutcomeUnknown` until observation proves success or failure. Read-only approved snapshots record their repository observation and result digest as one completed step rather than leaving an unjournaled reusable capability.
- `audit_log` — append-only `(audit_id, timestamp, cred_id?, approval_id?, presenter_id?, transport_peer, declared_scope?, method, args_summary, outcome)`. Null identities explicitly represent unidentified or rejected callers. Parseable attempts with a resolved repo go here; attempts without a resolvable repo go to per-user `user_audit_log`, so there is exactly one authoritative row per attempt.
- `thread_messages` — per-thread transcript rows. `(thread_id, change_id?, commit_id?, op_id?, session_id, seq, captured_at, author, direction, text, dedup_key, synthesized, anchor_unknown)` with `UNIQUE (thread_id, dedup_key)` and an FTS5 virtual table over `text`. CHECK constraint binding `anchor_unknown` to nullability of the `(change_id, commit_id, op_id)` triple. See [Transcript](../06-transcript.md).
- `thread_changes` — per-(thread, change_id) row carrying `tombstoned_at?` (abandon) and `redirected_to?` (squash).
- `transcript_offsets` — per-(thread, session_id) `(byte_offset, last_row_uuid)` for crash-safe tail resumption. Both fields advance in the same transaction as the corresponding `thread_messages` insert.
- `pending_kkd_prepends` — TTL-bounded `(prepend_id PRIMARY KEY, thread_id, text_sha256, inserted_at)`. Duplicate `(thread_id, text_sha256)` rows are allowed and consumed FIFO. Match key omits `session_id` so fresh-session reopens match correctly.
- `provider_egress_consents` — remembered, revocable grants `(consent_id, thread_id, provider_identity, purpose: 'catch_up' | 'transcript_mcp', disclosure_version, granted_at, granted_by_presenter_id, revoked_at?)`. Consent is valid only for the exact thread, configured provider identity, purpose, and disclosed policy version. Local preview is not provider egress; returning transcript-derived text through a hosted-model MCP call is and must check an active `transcript_mcp` grant before reading rows.

### v2-only

- `causal_chains`, `causal_chain_visits` — deferred until the broader MCP substrate ships. See [Roadmap](../16-roadmap.md).

## Constraints and transactional invariants worth calling out

- `threads`: `thread_head_commit_id`, `checkpoint_commit_id`, `checkpoint_change_id`, `checkpoint_op_id`, `bookmark_expected_commit_id`, `bookmark_expected_op_id`, and `owned_stack_base_commit_id` are required in `Active`, `ClosePreflight`, `CloseCommit`, `CloseFailed`, `Closed`, and `ProjectionDiverged`; destroy states retain every still-valid id until the corresponding journaled deletion or abandonment step. They may be null only while the corresponding creation step has not completed or after its exact destructive step is recorded. `bookmark_expected_commit_id` is the expected bookmark target, but need not equal `thread_head_commit_id` while active. `checkpoint_commit_id` must equal the latest `thread_checkpoints` row's `placed_commit_id`, and `bookmark_expected_commit_id` must equal that placement updated by its `thread_checkpoint_successions` rows on the agreed frontier; a placement resets the expected target to the placed commit in the same transaction that appends its row. Entering `Closed` sets the archived `thread_head_commit_id` to the close checkpoint's target and so requires `bookmark_expected_commit_id == thread_head_commit_id`. The equality must keep holding while `Closed`: a `SameChange` or `Reverted` succession for a closed thread moves the archived `thread_head_commit_id` in the transaction that appends it, and no other succession kind is valid there. A reopened thread's live head is the new empty working-copy commit `jj workspace add` creates on the checkpoint, so it reads `current`. Entering `Active` requires the ready-handshake transaction. The ready-handshake commit re-reads the launcher's OS identity and the open `terminal_servers` row before it enters `Active`. Staying `Active` requires no unresolved `thread_projection_issues`, no unfinished lifecycle operation other than a checkpoint operation (publish and detach run on `Active` threads), and a current `terminal_bindings` row in `Bound` whose `server_instance_id` is the current open `terminal_servers` row, with a live `agent` role in `terminal_panes`. It does not require a live incarnation: a harness that exited under a live launcher leaves the thread `Active` with `AgentStatus` `Crashed`, and it is never shown as working. `Closed` may have one unfinished or failed `Reopen` operation because reopen does not expose an active thread until its ready handshake commits; other lifecycle kinds are disallowed there. `ProjectionDiverged` requires at least one unresolved projection issue and `projection_resume_lifecycle IN ('Active', 'Closed')`; other states require it to be null. `CreateFailed`, `CloseFailed`, or `DestroyFailed` requires the corresponding failed unfinished lifecycle operation. A thread cannot return to `Active` from failed close until the journal records a verified resume of the frozen process set and its terminal binding, or an explicit restart repair; after destroy's first irreversible step, it cannot return to `Active`, `Closed`, or `ProjectionDiverged` by inference. Projection mismatches caused inside `Creating`, `CloseCommit`, reopen, or `DestroyCommit` belong to that lifecycle journal and fail the owning saga rather than manufacturing an invalid projection-resume state.
- `threads` bookmark name: a non-destroyed thread's bookmark name is unique within the repo. A rename normalization may not adopt a name another thread holds.
- `thread_checkpoints` and `thread_checkpoint_successions`: both are append-only. A succession row requires `from_commit_id` to equal the expected target in the parent view of `op_id`. `SameChange` and `PredecessorOtherChange` require the predecessor evidence the classifier names; `Reverted` requires `to_commit_id` to appear earlier in the same placement's history. `PredecessorOtherChange` is valid only for a thread whose lifecycle or `projection_resume_lifecycle` is `Active`. No succession row may be appended while the thread has an unresolved bookmark issue. Adoption through `kk repair` is a new placement row with reason `RepairAdopt`, never an edited succession.
- `terminal_bindings`, `terminal_panes`, and `process_records`: a partial unique index allows at most one non-`Ended` binding per thread, another covers `(server_instance_id, group_ref)` for non-`Ended` bindings so one Herdr workspace backs at most one binding, and another allows one live (`ended_at IS NULL`) pane row per `(terminal_binding_id, role)`. `Bound` requires a live `agent` pane row with `nonce_consumed_at` set. A pane row is inserted only in the transaction that verifies the presented nonce against `provision_nonce_hash` and sets `nonce_consumed_at`; the nonce cannot be reused for another binding. Ending a binding ends its pane rows and retires its non-retired `agent_sessions` rows in the same transaction, without acknowledging any intent. Retiring an incarnation does not end a pane row or a binding. Ending a `terminal_servers` row ends every binding that names it; because the two tables live in different databases, each repo database applies that rule when it next observes the instance change, before any binding of that instance is used. `process_records` rows are never deleted while the thread exists. A workspace-forget or directory-delete step may start only when every `process_records` row of the frozen set has `exit_verified_at`, the holder scan recorded with verified exit shows no holder other than the identities the approved plan accepted, and the post-exit filesystem recheck equals the final proof's journaled generation and fingerprint.
- `thread_lifecycle_steps`: `(lifecycle_op_id, ordinal)` is unique and step transitions are monotonic except that a failed idempotent step may return to `Started` with an incremented attempt. A lifecycle operation may have only one in-flight step. `Completed` requires `result_json` sufficient to recognize or compensate the external effect. Gate activation requires the credential, hook configuration, workspace head, bookmark checkpoint, and a `Bound` terminal binding whose `agent` launcher holds the gate claim, but does not enter `Active`. Only a ready-handshake transaction with a matching incarnation and settings fingerprint completes creation and enters `Active`; an activated gate alone is never success evidence.
- `thread_messages`: `(anchor_unknown=FALSE AND change_id IS NOT NULL AND commit_id IS NOT NULL AND op_id IS NOT NULL) OR (anchor_unknown=TRUE AND change_id IS NULL AND commit_id IS NULL AND op_id IS NULL)`. The two states cannot drift apart.
- `approved_operations`: `approval_id` is unique and immutable; `plan_digest` must equal the claimed approval's argument/rendered-plan digest. External steps cannot start before `state = Claimed`, and completion consumes the approval in the same transaction that commits the final result digest. `Failed` and `OutcomeUnknown` retain the claim and can only retry or observe the same step plan; they never release the approval for reuse.
- `sync_intents`: both exact base commits are required. `Materialized`, `Delivered`, and `Acknowledged` require a result workspace commit, byte-stable payload, complete anchor triple, and `prepared_at`. Before any soft-path workspace mutation, the transaction sets `delivery_mode = SoftBatch` and the complete `(barrier_incarnation_id, barrier_model_turn_id, barrier_tool_batch_id, barrier_bound_at)` tuple; partial tuples are invalid. `batch_completed_at` requires that tuple and may be written only by an idempotent completion report carrying the same identities. Soft acknowledgement requires both that completion and a later model-turn identity. If `MarkDelivered` was lost, that exact later-turn proof may atomically repair `delivered_at` and advance `Materialized -> Acknowledged`; a different batch or stdout alone is insufficient. `RestartStartup` clears the retired soft tuple without claiming acknowledgement, requires the complete `(restart_incarnation_id, restart_startup_delivery_id)` pair, and acknowledges only when that replacement's first managed boundary causally echoes the one-use id attached to the byte-stable startup message. `RecoveryRequired` requires `recovery_reason`, `recovery_bundle_path`, and `recovery_fingerprint`, and is entered only in the transaction that records those bundle fields. `result_has_conflicts` may be set only together with a result workspace commit, and `conflicts_cleared_op_id` only when it is set. Only a pre-materialization intent may become `Superseded`. A barrier tuple may be rebound to a new batch after a contrary delivery receipt only in a transaction that increments `soft_redelivery_count`; retry bounds are evaluated against that column and the persisted replacement-incarnation rows, never an in-memory counter. `delivery_exhausted_at` may be set only by the transaction that abandons the final permitted attempt; while it is set, exactly two writes are valid, both human-directed `kk repair` plans. A retry plan clears it, increments `delivery_epoch` (an integer starting at 0, monotonic per intent), records `delivery_rearmed_at` for display, and resets `soft_redelivery_count` in one journaled transaction. Every replacement attempt is stamped with the intent's `delivery_epoch` at creation, and attempt bounds count only rows whose stamp matches the current epoch — an exact id comparison, never a timestamp one, so clock skew or rollback cannot move an attempt between epochs. A re-armed intent therefore gets exactly one fresh cycle and may exhaust again. A one-shot-approved discard plan is the sole path to `Acknowledged` without delivery proof and must record the human resolution in `recovery_details`. Absent either plan, no new barrier tuple or replacement incarnation may reference the intent, restart recovery re-surfaces the blocked thread instead of retrying, and the thread's derived cascade status is `conflicted`.
- `agent_sessions`: `terminal_binding_id` must name a binding of the same thread, its launcher identity must equal the live `agent` row of that binding in `terminal_panes`, and its harness identity, once recorded, must differ from the launcher identity. A non-retired incarnation requires that binding to be non-`Ended`. `delivered_intent_id`, when non-null, must reference a same-thread `Materialized` or `Delivered` intent assigned to that incarnation's delivery mode. A partial unique index allows at most one non-retired incarnation to claim an intent. `thread_id` must equal the binding's thread. Starting a replacement process retires the old incarnation, records `startup_intent_id`, `startup_intent_epoch` copied from that intent's current `delivery_epoch`, and the saved payload hash before the harness starts, and supplies that payload as the first startup message. Delivery-attempt bounds count only rows whose stamped epoch matches the intent's current one. Its first managed boundary must re-prove exclusive hooks and the startup proof before atomically acknowledging and clearing both pointers. If the process exits earlier, the next replacement receives the same saved payload; no interrupted tool is replayed automatically.

## Migrations

Every schema change ships as a migration. Migrations are forward-only. Once a release is cut, schema changes must preserve upgrade compatibility. The migration runner is part of `kiki-core`.
