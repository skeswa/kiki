# Testing

Tests should target observable behavior and persisted state — what the system does and what it stores. They should not target private implementation details.

## Required high-value modules

[Orientation](01-orientation.md) is the sole ledger for which tier ships each surface; the two lists below only name the modules that need deep tests and do not assign scope. Modules behind the first-tier surfaces:

- `AncestryQuery`
- `OpAttribution`
- `CascadeOrchestrator`

- `TerminalRuntime`
- `TerminalClient`
- `ProcessSupervisor`
- `ConfigLoader`
- `ContextDiscovery`
- `AuthEnforcer`
- `ApprovalBroker`
- `LogRenderer`
- `StatusRenderer`

These modules are also required. Each one is tested alongside the later surface that ships it, as Orientation stages it:

- `AICompose`
- `MetadataLedger`
- `ThreadTranscriptStore`
- `SidebarController`
- `PaneLifecycle`
- `OverlayController` — opening and closing, NAVIGATE-mode transitions, preview-mode toggling (`t`/`d`/`c`), the chord ribbon adapting to the current selection, graceful degradation in narrow terminals, and mouse click-to-focus
- `ToastQueue` — expiry when a toast's TTL (time-to-live) runs out, dismissal on click, dismissal when the toast's action is invoked, dismissal when its row gains focus and is thereby acknowledged, and coalescing of cascade-applied events
- `FormController` — field navigation in the spawn card, and the approval-card flow that the daemon issues

## Regression tests for resolved spec conflicts

- `kk ls --all` includes closed threads. (A thread is kiki's unit of work: a named sequence of revisions in jj, the version-control system kiki drives.) It does not widen repo scope.
- `kk ls --all-repos` widens repo scope. It does so independently of lifecycle scope.
- Workspace isolation is cooperative, not a security boundary. (A jj workspace is an extra working directory attached to the same repository.) The docs say so, and no test claims security isolation.
- Kiki keeps its launch settings and centralized state outside the workspace, so they do not block `kk close`. The `.claude/settings.local.json` fallback is the one file kiki may own inside the workspace; kiki records a hash of the bytes it wrote there. `kk close` ignores that file only while it still matches kiki's recorded bytes.
- Untracked or ignored files that the user created still block or prompt during `kk close`.
- A turn-completion (stop) hook is installed only where its behavior is specified and tested. The Codex adapter's `Stop` lifecycle event is part of its specified contract. A Claude Code stop hook is not installed in v1 unless it is promoted with specified, tested behavior.
- Managed sessions of every v1 harness prove that kiki is the sole matching pre-tool hook. (A harness is the coding-agent program, such as Claude Code; a pre-tool hook runs before each of the agent's tool calls.) A project or user pre-tool fixture must not execute in the managed process. No test may claim that kiki merely runs before concurrently dispatched user hooks.
- Launch-scoped settings isolation leaves the tracked `.claude/settings.json` and the user's global settings byte-identical. Where the fallback is exercised instead, it merges only `.claude/settings.local.json`. It restores that file only from the expected kiki-owned hash. If the user edited the file concurrently, it reports that instead of overwriting.
- A managed Codex session launches under the generated `CODEX_HOME`, with authentication provisioned into it. The user's real `~/.codex/` configuration is untouched and unread. Hook fixtures from the workspace `.codex/`, from plugins, and from managed policy must not execute in the managed process. Nothing under `<workspace>/.codex/` is created, modified, or deleted. There is no workspace-merge fallback: a failed isolation proof fails the incarnation (one launch of the harness process) before the agent receives a prompt.
- The Codex adapter/version fixture proves its boundary before `parallel_batch_boundary` is claimed. The proof covers the following. No two tool calls of one turn run concurrently, and that includes calls originated by subagents. A new tool is requested only after the model has consumed the previous call's result. A deny decision returns the saved payload to the model byte-identically, and the denied tool never executes. When the hook sidecar is dead under an active barrier (a block that holds the agent's tool batch during reconciliation), the hook launcher answers with a generic blocking deny, so a barrier-covered call never fails open. A denied call fires no post-tool event. So the blocked single-call batch's `batch_completed_at` is recorded by the next turn-scoped hook event's admission transaction — a crash-surviving report driven by the harness — and never by the emitting hook's own RPC. Acknowledgement requires a `PreToolUse` with a distinct, serially later `tool_use_id`. A same-or-later Codex `turn_id` alone never suffices, because one `turn_id` spans many model steps. Acknowledgement always requires the delivery receipt: the session record's byte-identical deny result for the blocked `tool_use_id`. `MarkDelivered` alone never suffices. Crash and fault injection covers these cases. Hook death before stdout: the hook launcher answers with a generic deny, and the contrary receipt redelivers on the arriving batch. Stdout written but timed out or rejected by the harness: `MarkDelivered` is recorded, the receipt is contrary, and the intent is redelivered — never acknowledged. (An intent is the durable record of one unit of pending cascade work.) Persistent output rejection: a second contrary receipt for the same intent fails over to `RestartStartup` instead of redelivering again, and exhausted bounded restart attempts hard-pause with a loud attention event rather than looping. Daemon restart between and after those attempts: the attempt history and exhaustion state are read from the intent, so a restart after the first contrary receipt still treats the next one as the second, and a restart after exhaustion re-surfaces the blocked thread without minting a new attempt. The two repair exits: a `retry-delivery` plan re-arms exactly one fresh bounded cycle by incrementing the delivery epoch, so bounds count only attempt rows stamped with the current epoch — a prior-epoch row can never consume the fresh cycle, and no bound ever compares timestamps, even under clock skew or rollback — while a `discard-delivery` plan acknowledges without delivery proof only under a one-shot approval bound to that plan, and records the human resolution; no other write is accepted against an exhausted intent. Receipt unreadable at the completing arrival: acknowledgement defers when no delivery is pending, and takes `RestartStartup` when one is. Matching receipt: acknowledge. Beyond the fault cases, the generated config pins the harness-side hook timeout above the slow-path bound, and the fixture proves the session record durably contains deny results exactly as returned to the model. Every workspace-observing tool in the pinned version fires `PreToolUse` or is disabled by the generated config.
- Unrelated harness hook events stay enabled only for an adapter/version fixture that proves two things: they cannot race workspace reconciliation, and they cannot add another matching pre-tool hook.
- `kk init` is idempotent in an already-registered repo. It prints status and exits 0 without mutating anything.
- `kk init` does not pre-validate harness binaries. A missing-harness error surfaces only at `kk new` time.
- `kk init` succeeds when `gh` is missing or unauthenticated. The first GitHub-backed command performs the check. It reports an actionable error without corrupting local state.
- If a thread's workspace directory is deleted out of band, the thread records `ProjectionDiverged { reason: WorkspaceDirectoryMissing }` at daemon boot or `kk ls`. It fires exactly one notification. It is neither recreated nor reclassified automatically.
- Crash injection at every creation journal step leaves the thread in `Creating` or `CreateFailed`. Gate activation and harness start remain `Creating`. Only the matching ready handshake may enter `Active`. The pane launcher cannot pass its database-backed gate before the credentials, exclusive hooks, live head, checkpoint, and a `Bound` terminal binding are durable. Accepting a launcher and activating a gate are two transactions: the first accepts exactly one launcher for `(provision_id, role)`, records its OS-read process identity, and marks the binding `Bound`; the second records the incarnation and activates its gate, and is refused without a `Bound` binding. The provision nonce reaches the launcher only through its launch environment; it never appears in argv or in Herdr's saved state, only its hash is stored, and it is rotated before any re-issued create call. The harness is always the launcher's child, started from the launch specification `kkd` computed through `Harness::launch_spec`; the launcher never replaces itself with the harness. The launcher holds the child before exec until `ReportHarnessStarted` has recorded its identity, so a crash at any point leaves either no harness or a recorded one. The ready handshake arrives from `kk-hook` at the harness's session-start event, and its commit re-reads the launcher's OS identity and the open `terminal_servers` row; a launcher or server that changed in between fails the handshake.
- Launcher report acceptance. A `ReportLauncherStarted` is accepted only when the caller's peer-credential identity has the current server instance's process as its parent and a fresh per-pane process query shows the reported pane's root pid is that caller. Refused cases: a process that is not a pane root presenting a copied nonce; a launcher left over from a previous server instance reporting after a restart; a launcher reporting a pane id that belongs to another process; a second launcher for an already-claimed role; and a launcher reporting from a different Herdr workspace than the binding's first accepted launcher. Two non-`Ended` bindings can never name the same `(server_instance_id, group_ref)`. The final proof, before anything is terminated, includes a fresh observation showing that each listed container still holds the binding's recorded launcher process, or for a remnant or unbound container the exact processes listed in the approved plan; otherwise nothing is terminated and no close request is sent.
- Compensation limits. Automatic create and reopen compensation closes the provisioned group and removes the new jj workspace only while the gate was never activated, `ProcessSupervisor` shows nothing in the group but kiki's own blocked launchers, and the workspace still equals its initial materialization. A fixture that activates the gate, adds a `user` pane, or writes one file into the workspace before the failure stops the saga in `CreateFailed` (or the failed reopen state) with projections intact; cleanup then requires an approved repair plan that runs the close machinery.
- Harness exit versus launcher exit. When the harness exits under a live launcher, the launcher reports it, re-reads the atomically replaced thread credential, and awaits the next gate; the incarnation is retired without acknowledgement, `AgentStatus` is `Crashed`, the display state is `blocked`, the `agent` role and the thread's lifecycle are unchanged, and no surface shows the thread as working. A replacement incarnation is a new `agent_sessions` row and a new one-use gate claimed by the same accepted launcher, with no terminal provisioning. Kiki's own protocol restarts — a cascade hard restart or `RestartStartup` replacement — need no `HumanApproval`. The `kk repair` plan `restart-agent` restarts a crashed harness on the live launcher, uses `RestartStartup` when an intent is pending, and needs no approval in thread context. When the launcher itself exits, or its binding or server instance is lost, the `agent` role ends, the thread raises `TerminalMissing`, and the restart plan needs approval; in an agent-only group the launcher's exit also removes the Herdr workspace, and kiki reads that from a snapshot, not from a workspace-closed event. A harness killed without a report is found by `ProcessSupervisor` and handled as a harness exit. "The launcher answers" is tested as both conditions: its OS identity is alive and not stopped, and its supervision stream is open; a stopped launcher with an open stream does not answer.
- Replacement-incarnation remnant check. A retired harness leaves a tool child running in the launcher's descendant, session, or process-group set. The replacement's gate is not activated and no materialization runs; the thread raises `OrphanedProcess` with harness-remnant evidence. Hard-pause and `terminate` record and cover the harness's whole process tree, so the ordinary path leaves no remnant; the test injects one that escaped the tree but stayed in the session.
- Provisioning moves no viewer. With two clients attached to different terminal groups, creation, reopen, a terminal-restart repair, a replacement incarnation, and duplicate-group cleanup leave both clients where they were. This has not yet been run with attached clients at the candidate revision; it is an integration gate, not an assumed fact. The gate also records Herdr's known exceptions rather than hiding them: the first Herdr workspace created on an empty server takes focus; applying a layout over the active tab switches its viewers to the new tab; and a client viewing a replaced tab falls back to the server default.
- Provisioning after a lost reply: when the runtime's create or layout reply is lost, or the daemon crashes before the binding transaction, recovery takes a fresh snapshot and collects launcher reports before it issues any new call. A fault that produces two terminal groups for one `provision_id` ends with exactly one accepted launcher per `(provision_id, role)` and one gate claim. Every other launcher is refused and exits without starting anything. The duplicate group is closed only after `ProcessSupervisor` shows it holds nothing but refused, exited launchers; otherwise it stays and is reported as unbound. No fault order yields two harness processes.
- A runtime reply is never an outcome. Fakes return success for create, layout, input, focus, and close while the launcher never reports, the harness never becomes ready, the focus moved nobody, or a process survives. In every case kiki's state follows the launcher report, the ready handshake, the cascade protocol, or the `ProcessSupervisor` proof, and never the reply. Herdr's agent detection, `agent.wait`, and text accepted into a pane's input queue change neither `AgentStatus`, agent quiescence, the process quiescence proof, nor any delivery or acknowledgement state.
- Reopen keeps the thread `Closed` while its durable journal recreates projections. Its preflight verifies that the bookmark names `bookmark_expected_commit_id` — the latest placement updated by recorded successions — and recreates the jj workspace at that exact commit. The reopened head is the new empty working-copy commit on top of it, and the relationship reads `current`; a closed thread whose checkpointed commit was natively rewritten since close reopens at the successor without repair. Crash injection at every step either adopts the exact resource, compensates back to `Closed`, or records a stable repair plan. It never exposes `Active` before a matching ready handshake. Every new incarnation independently re-proves exclusive hook control.
- Close wants a quiet agent. Where the adapter proves agent quiescence, `kk close` preflight requires it: with a working agent, preflight reports that and exits with no mutation, no freeze, and no approval challenge. For an adapter version with `quiescence_detection: false`, preflight proceeds with a warning, and a working agent produces approval drift and a verified resume, never a loss. In both cases preflight takes the boundary snapshot so that the pinned head contains every tracked edit.
- Close takes its roots from every pane in the terminal group — role panes and `user` panes alike — plus every process identity recorded for the binding, and re-reads each root from the OS. A pane root is trusted only if its parent is the current server process. The freeze is write-ahead: each discovered identity is committed to `process_records`, with its prior stop state and the freeze's lifecycle operation id, before it is signalled. It freezes roots, descendants, session members, and process-group members to a fixed point. Its journaled steps run in this order: freeze; post-freeze recheck; checkpoint; each child step; final proof; termination of the frozen set with verified exit; terminal-group close request; post-exit filesystem recheck; workspace forget; directory delete. The **post-freeze recheck** runs immediately after the freeze and before the checkpoint, binds the frozen state to the approved fingerprint, and must show that no frozen member holds an open descriptor under the repository's `.jj` directory. The checkpoint pins the exact commit with a pinned, working-copy-ignoring jj command. Children are synchronously reconciled or detached. The **final proof** runs after the checkpoint and all child work and re-asserts that every member is stopped, plus membership, holders, the runtime pane set, the filesystem generation, and the fingerprint. The final proof is the recovery boundary: a failure at or before it takes the verified-resume path before returning `Active`, and a failed resume becomes `CloseFailed`; a crash after it resumes the idempotent journal forward and never returns to `Active`. Close never guesses from filesystem presence.
- Teardown order. Kiki itself terminates the frozen set while it is still stopped, before it asks the runtime to close the group. Per identity it confirms the process is still stopped and still the recorded `(pid, start_time)`, sends `SIGKILL`, and verifies the process is gone; a zombie counts as exited. A fixture that traps or ignores every catchable signal, and one that would be continued by a hangup, are both dead before the close request is sent, and neither runs a single instruction after the final proof. A process whose identity changed after it was stopped is continued and treated as unknown, never killed. Where the OS offers a process handle, signals go through the handle. The terminal-group close request is cleanup only, and its reply is never evidence. The **post-exit filesystem recheck** then requires the generation and fingerprint to equal the final proof's journaled values. It is re-read after a `kkd` crash, because the watch is lost with the process. Any mismatch is `CloseFailed` with files preserved; forget and delete do not run.
- Write-ahead freeze crash. `kkd` is killed after stopping some members and before stopping others, and again after the freeze completes. On restart the frozen set is rebuilt from `process_records`, never from memory or a re-discovery, and verified resume continues exactly the members recorded as previously running. No member is left stopped without a row, and no row names a process that was never signalled as one that must be continued.
- Frozen-step deadlines. Every step taken while the set is frozen has a deadline. A checkpoint, child step, or runtime call that exceeds it takes verified resume; the thread is never left frozen behind a stalled step. A frozen member holding a descriptor under `.jj` — a jj process stopped while holding repository locks — fails the post-freeze recheck and takes verified resume before any jj command is attempted.
- Destroy order: freeze; post-freeze recheck; final proof; termination of the frozen set with verified exit; group close request; post-exit filesystem recheck; then bookmark deletion; optional exact abandon; workspace forget and delete; credential revocation; tombstone. Drift before termination takes verified resume. Process termination is the first irreversible step; crash injection after it yields only `DestroyFailed` or completion of the same plan.
- Approval scope. A close, destroy, or restart approval covers every process in the listed terminal containers at freeze time. The rendered plan lists the preflight process inventory and states that scope. A process that appears in a listed container between preflight and freeze is terminated under that statement and is not drift. A workspace holder outside every listed container is accepted only when the approved plan names that exact identity; any other holder is drift.
- The process quiescence proof is the `ProcessSupervisor` freeze fixed point. Only close, destroy, and repair use it. The cascade's boundary is agent quiescence — the harness adapter's `AgentStatus::Quiescent` — and never the process freeze. Terminal observations satisfy neither.
- Process quiescence proof cases, driven through the `ProcessSupervisor` fake and repeated against real processes at the integration gate:
  - Fixed-point growth: a member that forks during discovery grows the set on a later round. The proof holds only after two identical complete samples with every member observed stopped. A set that does not stabilize within the bound is `Unknown`.
  - Prior stop state: a process that was already stopped before the freeze stays stopped after an aborted close. A process that was running is continued.
  - A root whose OS start time disagrees with the record is a different process. It is treated as unknown, never as the recorded one.
  - Unknown holder: a same-UID process outside the frozen set that holds the workspace makes the result `Unknown` unless the approved plan names that exact identity as accepted. Files are preserved. The result reports each offending pid, its command line, and the step that clears it. `kkd`, its child processes, and the invoking `kk` are excluded from the scan. A process running as another user is invisible to the scan, and no test or message claims otherwise. A member stopped by a debugger makes the result `Unknown`. An unrecorded holder never blocks an `Active` thread's cascade boundaries and raises no standing issue.
  - Split during freeze: a pane or tab added to the terminal group after the freeze is drift at the final proof. Where the runtime advertises `mutation_fence`, the split is refused instead. Neither case proceeds to an irreversible step. Without a fence kiki detects pane-set and tab-set changes only; it makes no claim about terminal input sent to a frozen pane.
  - Drift found by the post-freeze recheck or the final proof — a changed member set, a new holder, a changed runtime pane set, a new filesystem generation, or a changed fingerprint — preserves files and takes the verified-resume path.
  - Verified resume: members are continued children before parents, session leaders last. Every member keeps its recorded identity, and none that was running is left stopped. Resume requires the role-launcher identities and the terminal group, and the `agent` launcher must answer. A `user`-pane process that exited during the freeze is reported and is not a failure. Only then may the thread return to `Active`. An unprovable resume is `CloseFailed` with the workspace present. If a tool batch was in flight when the freeze began, the incarnation's batch state is unknown after resume and the unknown-batch rule applies: hard restart to a clean boundary with files untouched.
  - Verified exit: exit is verified per recorded identity by kiki's own termination, before the runtime is asked to close anything. A fake runtime that replies success to a close request while a process survives, and one that never replies, change nothing: workspace deletion depends only on every frozen identity being gone, the holder scan, and the post-exit filesystem recheck. If exit cannot be verified, the files stay and the lifecycle fails loudly.
- A close approval is bound to the rendered plan and the preflight fingerprint. Drift discovered after the freeze causes a verified resume and a fresh plan and approval. The daemon never prompts while leaving a terminal group frozen.
- Workspace-record, path, bookmark, and terminal mismatches all produce durable projection issues. Only a unique, identity-preserving normalization may auto-repair. Every ambiguous plan uses a stable repair id, and that id goes stale when the observed state changes. Bookmark-only divergence continues safe workspace-head tracking and follows classification. Terminal divergence continues observation but suspends boundary mutation. Workspace identity or path ambiguity suspends both.
- `TerminalMissing` is raised for each of its causes: a missing or changed server instance, a server instance `kkd` did not start, a missing terminal group, an ended `agent` role launcher, a cold restore, and an observed live handoff. A role is bound to the claiming process identity `(pid, start_time)`: it survives a `shell` or `ui` launcher replacing itself with the shell or UI program, and it ends when that identity ends. A pane with no claiming identity has no role; `user` names that absence. While `TerminalMissing` is open, boundary delivery, materialization, and lifecycle mutation are blocked, except for approved restart, `close-without-terminal`, and destroy plans. A matching Herdr workspace, tab, or pane id, label, working directory, or metadata token on a different server instance never rebinds a thread.
- No container reuse. A terminal restart never binds a remnant or unbound container, whatever its label or working directory. The restart plan lists every remnant or unbound container whose processes hold the workspace, with those processes, for approval; closes each through freeze, termination with verified exit, and a close request; re-runs the holder scan; and provisions a fresh terminal group with new launchers. The same steps run in `close-without-terminal` and in destroy from `ProjectionDiverged`. A restored login shell sitting in the jj workspace is found as a holder and listed, never adopted and never silently killed.
- Context resolution. Resolution by Herdr pane identity succeeds only when `kkd` verifies from the CLI connection's peer credentials that the caller is a descendant or session member of that pane's root process on the current server instance. Refused cases: ids copied into an unrelated process's environment; ids from another Herdr server; ids left stale by a native pane move; ids from a previous server instance. A popup or keybinding invocation resolves through `HERDR_ACTIVE_*` only as a locator for read-only and navigation commands; a mutation invoked that way still requires the thread credential and any approval. Herdr ids never substitute for a credential.
- Presenter under an agent. `ConfirmApproval` is refused when the presenter process is a descendant or session member of any recorded `agent`-role launcher, including a presenter started by an agent's tool call in its own pane. The same presenter in a `shell` or `user` pane is accepted.
- Harness environment. The harness process and its tool children see no `HERDR_*` variable; the `agent` pane keeps `KIKI_THREAD_ID`. No pane of any role sees a redirected `XDG_CONFIG_HOME` or `XDG_STATE_HOME`, or a variable that came from the terminal that happened to invoke `kk`, such as that terminal's `TERM_PROGRAM`, window id, or multiplexer variables: panes inherit only the constructed login baseline, Herdr's own variables, and the role's explicit variables. `HERDR_CONFIG_PATH` is visible in panes and the test records that as expected.
- Server start and configuration. `kkd` regenerates the Herdr configuration file and validates it with its own parser immediately before every server start. A file rewritten by Herdr's settings screen is replaced. A generated file that fails validation prevents the start; the server is never started on a file that Herdr would silently replace with defaults, because those defaults turn agent resume on. The start uses `--session` and `HERDR_CONFIG_PATH` only. `kk attach` connects in connect-only mode and, with no server running and `kkd` unreachable, fails instead of starting a server. A server that `kkd` did not start is unverified: nothing is provisioned on it and its threads read `TerminalMissing`.
- Service placement. On macOS `kkd` runs as a launchd user agent and starts the Herdr server from there; on Linux it is a systemd user unit. With `kk` first invoked from inside a terminal application, quitting that application leaves `kkd`, the server, and every agent running. This is an integration gate on each platform. No Herdr release containing its own terminal-quit fix is required, because that fix applies only to a server Herdr starts for itself.
- Cold restore: the dedicated server stops and restarts with its saved layout. The fake and the real runtime both return the same public workspace, tab, and pane ids with new processes, and may reuse a closed group's workspace id for a new group. Launch argv is saved but not rerun; launch environment and tokens are not kept; a restored pane whose saved directory is gone has no process. Kiki records a new `server_instance_id`, ends every binding from the old instance, retires every incarnation without acknowledgement, runs the orphan scan, and raises `TerminalMissing` for each affected thread. No restored pane is ever reported `Active`, `kk status --no-jj` and `kk ls` do not show a ready agent for it, and no boundary mutation runs against it. Kiki publishes no label to a remnant container. The generated Herdr configuration disables automatic agent resume, and a fixture with a resumable harness session proves the runtime starts no agent on restore. A restart happens only through an approved `kk repair` plan with a fresh credential, launch settings, gate, and handshake, in a freshly provisioned group.
- Daemon restart with a surviving server: `kkd` reconnects, verifies the `server_instance_id` against its record, snapshots, and reconciles. Bindings whose recorded process identities are still live under the same instance continue without a new incarnation.
- Orphan recovery: a worker that ignores hangup survives a `SIGKILL` of the dedicated server and is absent from every terminal view. The orphan scan at daemon start, at the instance change, and before a replacement finds it by recorded identity and raises `OrphanedProcess`. The fixture's worker is a recorded identity — the harness itself. A second fixture uses a tool child that kiki never recorded: it raises no `OrphanedProcess`, and instead the `restart-terminal` plan's holder scan reports it by pid and command and stops until the plan names it as accepted or it is gone; kiki does not signal it. While the issue is unresolved, kiki activates no gate and materializes nothing in that workspace. The approved repair plan stops, re-verifies, and terminates only the exact recorded identities and verifies their exit. Recorded role processes that are pane members on the current instance are terminal members and raise no orphan issue. An unrecorded same-UID holder raises no standing issue; it surfaces only as an `Unknown` result in an operation that would delete the workspace.
- Event loss and resync: the runtime fake reports lost events, drops the connection, and changes instance between a subscription and its snapshot. In every case `kkd` resubscribes, takes a fresh snapshot, reconciles every binding against the snapshot and the OS, and republishes presentation. No decision is reconstructed from the runtime's event history. A label renamed by another socket peer is republished to its bound terminal group and is never read back as input. The matching cases for sidebar tokens — overwritten, expired, or lost at restart, then republished — are tested with the later sidebar-token surface, not here.
- Caller-local focus with two attached clients: with `client_targeted_focus` advertised, `kk switch <thread>` moves only the invoking client; the other client's location is unchanged. A command with no viewer — an agent's tool call, a script, a pane nobody is showing — resolves `NoCallerClient` and moves no one. Without the capability, `kk switch <thread>` fails naming the missing capability and moves no client; it never falls back to the broadcast focus. `kk switch --all-clients <thread>` is the only form that moves every attached client. Capability detection reads the runtime's advertised capabilities; a fake that silently ignores the unknown client parameter must not be mistaken for support. No form of switch creates, closes, or re-ensures a pane, and none consumes a `HumanApproval`.
- A `TerminalMissing` repair can restart the thread to `Active`, or execute a stable `close-without-terminal` plan to `Closed`. That plan's loss inventory runs in preflight. Claiming its approval enters `CloseCommit`. Listed remnant and unbound containers that hold the workspace are frozen and rechecked — which records their identities — and then terminated with verified exit and closed, as journaled `CloseCommit` steps; then come the holder scan, the checkpoint, child steps, the final proof, the post-exit filesystem recheck, forget, and delete. An abort before the first irreversible step takes `CloseCommit --> ProjectionDiverged`, mirroring `DestroyCommit`. Crash injection at each step resumes the same plan and never returns the thread to `Active`.
- `kk-hook` returns the harness's non-blocking decision (Claude Code's `continue`, Codex's `allow`) and writes to `~/.config/kiki/repos/<repo_id>/errors/<thread_id>.log` when it cannot reach `kkd` within its connect and overall budget. It does not block the agent's tool call. A reconciliation pending during the outage must still be delivered on the next successful PreToolUse round-trip. If the watcher saw the trigger, durable state lives in `sync_intents`. Otherwise, restart catch-up reconstructs it from jj's op log (jj's record of every operation run against the repo). If the agent edited the stale tree during the outage, the next probe enters `RecoveryRequired` rather than treating the tree as clean.
- Once a cascade delivery barrier is active, a daemon outage no longer lets tools pass through. Every call in that tool batch stays blocked until a matching `PostToolBatch` completes the barrier or the adapter takes the hard-restart path.
- The `Block` admission and the complete soft-barrier identity commit before the first reconciliation mutation. Crash injection between every probe, jj, filesystem, and SQLite step must never leave changed files with an unbound batch.
- Native ancestor evolution: amending thread A causes jj to evolve thread B's repository working-copy commit. The classifier records `NativeRewrite` with the exact old-base → evolved-base ids. It performs no redundant rebase. At B's safe boundary, it verifies that B's current commit still contains that base before materializing it (updating B's files to match).
- Parent-head advance: adding revision A2 in A's managed workspace updates A's persisted live head, while A's checkpoint bookmark remains on A1 and `bookmark_expected_commit_id` does not change. No bookmark issue is raised, and once A2 has content or a description status shows the relationship `behind`. The classifier records `ParentAdvance` from the exact live head. B's boundary rebases only the validated single-parent owned chain. Merge, multiple-root, or foreign topology stops as `TopologyDiverged`.
- A successful `ParentAdvance` persists B's actual result as `threads.thread_head_commit_id`, in the same transaction as the materialized intent. The watcher does not re-trigger cascade for the attributed jj operation, and the head advance is not lost; checkpoint classification still runs on it.
- Multi-workspace cascade in A→B→C: one jj operation may logically evolve both B and C. Both receive independent `NativeRewrite` intents immediately, from comparing the before and result operations. B and C materialize at their own boundaries. If an explicit advance of B evolves C, the initiating reconciliation handler records C's intent, even though the watcher does not re-trigger cascade for the attributed op.
- Direct human materialization: a person may run `jj workspace update-stale` directly in stale B. In a non-colocated repository that changes B's files without creating a new op-log head; in a colocated repository it also records a "reset git head" operation, which the watcher classifies as no base transition. In both cases the boundary probe detects `FreshClean` or `FreshDirty`, performs no duplicate update, and still delivers context for the unresolved intent.
- Coalescing updates one pre-materialization intent's base transition and its normalized trigger rows. Once payload preparation begins, later work receives a new ordered intent and cannot mutate the saved delivery.
- A stale workspace with unsnapshotted edits, or an `Unknown` probe result, enters `RecoveryRequired`. Recovery hard-pauses the agent and enumerates divergent successors outside the workspace. It never resumes on a clean successor that hides those edits. The `JjBackend` fake and real jj both return success from a dirty `jj workspace update-stale` while the edited file is gone from disk and present only in the other divergent successor; the test fails any implementation that treats that exit status as preservation.
- Watcher restart from a multi-parent or divergent jj operation graph traverses all reachable, unprocessed ancestors from the persisted frontier, in topological order. Tests must fail any implementation that stores one parent or advances one linear cursor through the operation DAG.
- Pinned reads: every observation kiki makes of a managed repository names a full operation id and ignores the working copy. Against real jj, with a dirty working copy and with two and three operation heads, a complete watcher pass, a projection audit, `kk ls`, the `kk status` header, and `kk status --no-jj` create no operation, snapshot nothing, and leave the head set byte-identical. The human passthroughs are the exception: the `kk` CLI, never `kkd`, runs the body of `kk status` and the overlay's `d` diff for the contextual thread in the caller's contextual workspace, and they may snapshot like any direct jj use. The `JjBackend` fake fails any read issued without an exact operation id, and any read issued with `--at-op=@`.
- Frontier sampler: the `OpFrontierSampler` returns every head for one, two, and three heads, from the main workspace and from an added workspace whose `.jj/repo` is a pointer file. A watch on the parent of the head store is shown to miss head changes. An unrecognized store marker or jj version yields `Unavailable`; the watcher reports itself degraded, `RefreshToFrontier` fails closed, and no `jj op log` fallback runs.
- Unmerged frontier: while two heads disagree about a thread's `@` or bookmark, the row caches keep the last agreed value, status prints "frontier unmerged" instead of a checkpoint relationship, and no projection issue is raised from one head's view. A lifecycle command that needs one view integrates deliberately, records the resulting operation in `op_attribution` with kind `Integration`, and still classifies it as a multi-parent operation. When an external command merges the heads first, the merge operation is classified the same way.
- Pinned mutation: bookmark moves, rebases, abandons, pushes, and `jj workspace forget` run at the exact head their plan validated with the working copy ignored. `jj workspace add` runs at that exact head without `--ignore-working-copy`, writes the workspace and its initial working-copy commit as two operations, and, run while the main workspace is dirty, snapshots nothing there. An external operation injected between validation and mutation yields two heads and never a silent merge; the next sample observes both, and the saga re-validates instead of assuming its view. A placement that lands beside a concurrent operation applies only to views that descend from it, and the journal that made it re-places deterministically at the first integration operation instead of raising an issue. The only unpinned commands are the closed list in [Invariants](02-invariants.md#operation-history-is-a-dag): the working-copy commands, deliberate integration, and the human passthroughs. Each working-copy command `kkd` runs is taken under its lock only after a single-head sample, is attributed, and is followed by a new sample.
- Checkpoint succession, same change: after `kk new`, the first edit and snapshot rewrites the checkpointed commit and jj moves the bookmark. Kiki appends a `SameChange` row to `thread_checkpoint_successions`, advances `bookmark_expected_commit_id`, leaves `checkpoint_commit_id` and `thread_checkpoints` unchanged, and raises no issue. The same holds for `jj describe`, a rebase, a squash into the bookmarked commit, and an ancestor rewrite made from another workspace. A chain across several unprocessed operations is proved one operation at a time.
- Checkpoint succession, other change: `jj split` of the bookmarked commit, and a squash of the bookmarked commit into its parent, move the bookmark to a commit with a different change id. For an `Active` thread the move is accepted as `PredecessorOtherChange` only when the operation's predecessor record names the old target and the new target is the exact live head or on the validated owned chain. Off the owned chain it is `BookmarkMoved`. For a `Closed` thread every different-change successor is `BookmarkMoved`. Squash variants: squashing the bookmarked commit into its child, or into an earlier commit on the chain, moves the bookmark to the old target's parent while another commit records the predecessor; for an `Active` thread that is accepted when the new target is on the validated path and a commit on that path, or the live head, records the old target as a predecessor, and the row names that evidence commit. Evidence may come from the classified operation or from an ancestor of it that is not an ancestor of the operation that established the expected target.
- Closed-thread succession: an ancestor rewrite from another workspace rewrites a closed thread's checkpointed commit. Kiki accepts the `SameChange` successor and advances the archived `thread_head_commit_id` in the same transaction, so `bookmark_expected_commit_id == thread_head_commit_id` still holds and the thread stays `Closed`.
- Successor evidence is required: a move to a commit with the same tree or description but no operation predecessor record, a move while the old target is still visible, and an operation whose predecessor record is absent are each `BookmarkMoved`. `jj bookmark move`, a sideways move, and a backward move that is not an undo of a tracked rewrite are `BookmarkMoved`.
- `BookmarkConflicted`: two operations that each rewrite the checkpointed commit merge into divergent successors and a conflicted bookmark; so does a dirty `jj workspace update-stale` on a workspace whose `@` carries the bookmark. Both are `BookmarkConflicted`, never a chosen successor. The conflict flag is tested before the unchanged-target rule: a bookmark that jj marks conflicted while its only target is still the expected target — after one divergent side is abandoned, or after a fetch that deleted the tracked remote bookmark while the local one had moved — is `BookmarkConflicted`, not unchanged.
- External bookmark rename: one operation that removes the thread's bookmark name and adds exactly one new local name on the expected target is a normalization, provided the operation changes no remote or `@git` bookmark and is not an import or fetch. Kiki adopts the new name on the thread row, appends a `thread_bookmark_renames` row, appends no placement row, raises no issue, and keeps the thread's lifecycle. Each weaker case is `BookmarkMissing`: two new names in that operation, a new name on a different target, a name another thread already holds, a delete followed by a create in a later operation, the old name still present in the view, a fetch or colocated Git import that removes one name and adds another on the same commit, and a rename of a published thread, whose tracked remote bookmark keeps the old name.
- `jj abandon` of the checkpointed commit deletes the bookmark and is `BookmarkMissing` with evidence `CheckpointAbandoned`. A fetch after a merged pull request's branch was deleted abandons the unreachable checkpointed commit and deletes the bookmark; that is the same issue, for an active thread and for a closed one. Its plans are to make the commit visible again and re-place the bookmark on it, or, for a closed thread, to destroy. When the abandoned commit is also a live head or an owned revision, follows classification records `TopologyDiverged` independently; neither result suppresses the other.
- While a bookmark issue is unresolved, later bookmark observations are recorded on that issue and no succession row is appended. Head tracking and follows classification continue. The issue resolves automatically, with no plan, when a later operation shows the bookmark unconflicted on the expected target.
- Undo rule: after a tracked `jj describe` rewrite, `jj undo` returns the bookmark to the earlier commit while the later one becomes hidden. Kiki appends a `Reverted` succession row, sets the expected target back, and raises no issue. `jj redo` is handled the same way, and so is `jj commit` followed by `jj undo`. A backward move to a commit that is not in the placement's own history, or while the later commit is still visible, is `BookmarkMoved`.
- Restore never targets a hidden commit: for `BookmarkMissing`, `BookmarkMoved`, and `BookmarkConflicted`, no restore plan is offered while the expected target is hidden, and a test that forces one shows the divergent change it would create and fails.
- Checkpoint target rule: every checkpoint places the bookmark on the live head, or on its parent when the head is an empty, undescribed working-copy commit whose parent is on the owned chain. Creation places it on the initial commit itself. A checkpoint whose target is neither equal to nor a descendant of the expected target refuses without mutating; only a separately approved backward or sideways plan passes `--allow-backwards`.
- Checkpoint relationship: `current` when the expected target equals the head, and when the head is an empty, undescribed working-copy commit on top of it (right after `jj commit` and right after `kk reopen`); `behind` for any other descendant head; `ahead` after `jj edit` of an earlier commit; `diverged` otherwise. An unregistered descendant of the chain changes neither the relationship nor successor tracking; it blocks only rebase and abandon plans.
- Classification runs on kiki's own operations: an explicit `ParentAdvance` rebase that carries a child's and a grandchild's bookmarks appends a succession row for each affected thread, while opening no second cascade intent for the attributed operation.
- Attribution: kiki sets no operation description. Each kiki-run command carries a per-invocation operation user and host, and every operation id it wrote is recorded, including both operations of one `jj workspace add`. An external operation is never attributed, whatever its description says.
- Operation history rewritten: after `jj op abandon` and `jj util gc` leave no frontier head descending from a recorded operation, kiki re-anchors silently when every thread's bookmark and every workspace `@` equal their cached values. When any differs, it raises exactly one repo-level `OperationHistoryRewritten` issue listing those threads, raises no per-thread bookmark issue for the gap, and blocks checkpoint, publish, close, detach, and explicit rebase for the listed threads until the repair plan re-anchors.
- Boundary snapshot: it is taken at agent quiescence or a held harness boundary — or, for a harness that cannot prove quiescence, at a lifecycle preflight — under the thread lock, after a single-head sample, and it is attributed and followed by a new sample. Close, detach, and publish preflight take it so the pinned head contains every tracked edit. A `ParentAdvance` whose probe returns `FreshDirty` takes it and proceeds only when the second probe returns `FreshClean`; `StaleDirty` and `Unknown` never take it and go to recovery. The probe itself never snapshots.
- Textual conflicts: a reconciliation whose result contains jj conflicts sets `result_has_conflicts` on the intent and adds no state. The payload lists the conflicted commits and paths and says they must be resolved. Derived cascade status is `conflicted` before and after acknowledgement, and it leaves `conflicted` only when a later operation's view shows the thread's chain conflict-free. A textual conflict alone does not hard-pause the agent.
- Replacement incarnation precondition: a replacement's launch gate is not activated while a tool child of the retired harness survives in the `agent` launcher's descendant, session, or process-group set. The survivor raises `OrphanedProcess` with harness-remnant evidence and blocks the gate and workspace materialization. A hard-pause terminates the harness's whole process tree by recorded identity and leaves the launcher alive. Cascade restarts need no human approval.
- `restart-agent`: a harness that crashed under a live launcher is restarted by this `kk repair` plan on the same launcher through a fresh gate, with `RestartStartup` when an intent is pending, and without approval in thread context. When the launcher itself is gone the intent waits behind `TerminalMissing` repair.
- Unknown batch after a freeze: when a tool batch was in flight at the start of a close, destroy, or repair freeze and the operation takes verified resume, the incarnation's batch state is unknown. Kiki hard-restarts it to a clean boundary with files untouched and performs no mid-batch mutation.
- A journaled lifecycle checkpoint appends exactly one `thread_checkpoints` row and resets the expected target to the placed commit. A checkpoint placed on a workspace with unsnapshotted edits is followed by a `SameChange` succession at the next snapshot, not by an issue.
- Creating a follows edge and detaching one both pin an exact operation view. Both synchronously refresh the affected live heads before choosing or discarding an anchor. A lagging asynchronous watcher cannot make either command lose a parent or child advance.
- `kk thread destroy` deletes kiki projections and records only after an exact plan is confirmed. It preserves jj revisions by default. `--abandon-revisions` may abandon only the validated, unreferenced, single-parent owned chain named in a separate approved plan. It refuses shared, foreign, followed, or ambiguous topology.
- Destroy crash injection — before and after bookmark deletion, optional exact revision abandonment, terminal-group and workspace cleanup, and tombstoning — yields only the recorded `DestroyCommit`, `DestroyFailed`, or `Destroyed` outcome. After the first irreversible step, no recovery path relabels the thread `Active`, `Closed`, or `ProjectionDiverged`. `kk repair` can only finish the exact approved plan, or invoke explicit jj operation recovery where that applies.
- `LogRenderer` and `StatusRenderer` produce output that stays readable in monochrome when `NO_COLOR=1` is set. Every state in the cascade, agent, and lifecycle vocabularies has a distinct glyph or label that does not depend on color.

## Cascade crash tests

A cascade is how kiki carries a parent thread's changes into the threads that follow it. The cascade tests must cover:

- a hook crash before it writes stdout
- a pre-stdout hook crash followed by a newly enqueued cascade
- a crash between stdout and `MarkDelivered`
- a crash after `MarkDelivered`
- two or more concurrent `PreToolUse` calls racing to reconcile the same intent; exactly one materialization occurs, and every call in the triggering batch is blocked
- permutations in which each logical tool is the first hook to arrive for a batch with pending work; whichever arrives first fixes `Block`, and no arrival order lets a sibling tool execute
- a batch whose first admission is `PassThrough`; an intent detected before a later sibling hook is deferred to the next batch, rather than partially blocking a batch that was already admitted
- a hook launcher or daemon restart after a `PassThrough` admission loses the cache; an unknown in-flight batch leaves files untouched and hard-restarts the incarnation to establish a clean boundary, while an active durable `Block` stays fail-closed
- a concurrent sibling `PreToolUse` arriving after payload emission but before `MarkDelivered`; it receives the byte-identical payload and cannot acknowledge the intent
- matching, duplicate, stale, missing, and reordered `PostToolBatch` events; only the matching event marks batch completion, and none of them acknowledges delivery
- a new batch in the same model turn after `PostToolBatch`; it cannot acknowledge merely because its batch id differs
- the first `PreToolUse` from a provably later model turn acknowledges the delivered intent, then evaluates the next ordered intent before deciding whether its tool may run; if `MarkDelivered` was lost, the same exact proof atomically repairs delivery and advances `Materialized -> Acknowledged`
- hook, daemon, and agent crashes before and after durable barrier creation, and before and after `batch_completed_at`; ambiguous completion always hard-restarts with the saved payload
- the hard-restart fallback when an adapter cannot expose an unambiguous batch-completion boundary: the replacement row and the byte-stable startup payload are durable before the harness starts, the payload is the replacement's first startup message, its first managed boundary proves startup processing before acknowledgement, and no interrupted tool is replayed automatically
- an agent crash after delivery but before acknowledgement
- a resume with a delivered-but-unacknowledged intent
- multiple cascades before the first hook, coalescing into one delivery
- deliverable-intent lookup and byte-identical retry for both `Materialized` and `Delivered`
- daemon crash and recovery at every `sync_intent` state, including `RecoveryRequired`
- `WorkspaceProbe` returning `FreshClean`, `FreshDirty`, `StaleClean`, `StaleDirty`, and `Unknown`, plus fingerprint drift immediately before mutation
- `jj workspace update-stale` with clean files, with unsnapshotted edits (a successful exit that leaves the edits only in another divergent successor), with conflicts, with direct materialization that creates no new operation, with direct materialization in a colocated repository that creates one, and with a concurrently advanced base transition
- recovery verifies edit-bearing divergent successors before choosing the visible result; ambiguous recovery requires a human to choose
- a process restart with a reused harness session id retires the old runtime incarnation without acknowledgement, re-proves exclusive hook control, and injects the saved payload before any replacement-process tool may run; a crash before its first boundary redelivers to another replacement
- `--no-integrate-operation` plus `jj op integrate` feasibility for a planned `ParentAdvance`, including concurrent external operations

They must also cover the six worked scenarios in [Cascade](05-cascade.md#worked-scenarios): a clean ancestor rewrite, an ancestor rewrite after an agent edit, a parent adding a revision, direct human reconciliation, an agent crash after delivery, and a parallel tool batch. These are scenario tests over observable state, not assertions about private function boundaries.

## Module-specific obligations

`MetadataLedger` tests cover content-hash ownership, trailer independence, sticky renames of human bookmarks, squash inheritance toward human ownership, and opt-back-in refresh.

`AuthEnforcer` and `ApprovalBroker` tests cover thread-scoped rejection across siblings and operational rejection of Admin. They cover broker enrollment; persisted begin/display/confirm/cancel challenges; binding of the nonce, channel, method, target, arguments, and rendered plan; atomic capability issuance after confirmation; atomic claim with one durable operation id; crash resume of only that plan; final consumption; expiry and replay; plan-digest drift; and non-interactive failure. Audit tests cover accepted, rejected, unidentified, bootstrap, registration, invalid-repo, and `ListRepos` attempts. Each attempt writes exactly one row, routed to the per-repo or per-user SQLite sink, with nullable credential and approval identities represented explicitly.

`ThreadTranscriptStore` tests cover FTS (full-text search); author and direction preservation; change-aligned reads; tombstoned and redirected changes; recovery from JSONL rotation and truncation; offset and row insertion in one transaction; prevention of reopen catch-up recursion; `pending_kkd_prepends` FIFO matching; idempotent cascade-injection rows; and intent-pinned anchors. Provider-egress cases cover first consent, remembered consent, revocation, a configured-provider change, local preview without egress, and denial of same-thread transcript MCP until an active purpose-bound grant exists.

`LogRenderer` tests cover stack-aware expansion, collapsed siblings and unrelated threads, `--no-stack`, `--all`, `--wide`, `-r <revset>` disabling collapse, and parser errors when `-r` is combined with collapse flags.

`StatusRenderer` tests cover the exact live head; the checkpoint bookmark and its expected commit (`bookmark_expected_commit_id`); the `current | behind | ahead | diverged` checkpoint relationship computed purely from that expected commit and the live head, including `current` right after `jj commit` and `kk reopen`, `behind` once the head has content or a description, `current` after a tracked native succession, `ahead` after `jj edit` of an earlier commit, and `diverged` for every other relation; unresolved bookmark issues listed by name beside the relationship without changing it; "frontier unmerged" printed in place of the relationship while heads disagree; omission of unavailable v1.x PR fields; follows and children rows; the three-valued cascade state; `--diff`; `--diff --stat`; and `--no-jj`.

`TerminalRuntime` tests cover capability derivation from the version, protocol, and object of named flags the ping reply returns, including that `live_handoff: true` is not read as support; `ensure_server` with configuration regeneration and validation; rejection of a handle from another server instance before any call; the provisioning protocol under lost replies and crashes; `subscribe`-then-`snapshot` ordering, with the snapshot built from the session snapshot plus per-pane process queries and re-read from the OS; a capability-gated `fence` whose returned guard releases the fence when dropped; one-way presentation publishing; and `notify` as a global toast whose reply is not a display receipt. `TerminalClient` tests cover caller resolution, the three `FocusOutcome` values, verification of the server's peer identity against the terminal target, and `kk attach` connecting in connect-only mode to the named session after `kkd` ensured the server. `ProcessSupervisor` tests also cover `terminate` taking recorded identities through stop, verify, kill; `reprove` over a `FrozenSet` rebuilt from rows; and the filesystem watch handle belonging to the `FrozenSet`. `ProcessSupervisor` tests cover every result type's `Unknown` outcome and the evidence each result carries.

`SidebarController`, `OverlayController`, `ToastQueue`, `FormController`, and `PaneLifecycle` tests cover navigation versus consequential-action gating, contextual-thread previews versus exact sibling-read approval, daemon-issued approval cards, disconnected and reconnecting rendering, cursor preservation across event streams, toast TTL/click/action behavior, spawn form navigation, terminal-too-narrow warnings, and rejection of repo-shared `[ui]` config. `PaneLifecycle` covers the `shell` and `ui` role panes: each is ensured at creation, at `kk reopen`, and at a terminal-restart repair; neither is re-ensured at `kk switch` or respawned after the user closes it. `SidebarController` drives the Stack tree in the optional `ui` role pane, which never receives a toast. `LogRenderer`, `StatusRenderer`, the overlay, and the `ui` pane render lifecycle, cascade, and agent display states through one shared renderer; a golden test asserts that the same summary row produces the same glyph and label on every surface. If that pane is the only visible kiki surface, eligible events use the OS-notification fallback, while durable row state remains visible.

Publishing tests prove that the first publishing tranche uses a human-authored or static template, not transcript or AI drafting. Parent-merge local reconciliation may complete without approval. Force-push and PR-base mutation remain a pending named remote plan until a foreground one-shot approval claims it. A failure retains the follows edge and is safe to retry.

## Fakes

Deep-module tests should use fakes — stand-in implementations that act like the real dependency but run in-process — for:

- `JjBackend`
- `TerminalRuntime`
- `TerminalClient`
- `ProcessSupervisor`
- `GitHubBackend`
- `Harness`
- `TranscriptAdapter`
- notification sink
- clock
- filesystem event source

The fakes should expose edge cases directly: op storms, hook crashes, parallel tool batches, concurrent hook arrival, missing and reordered batch completion, model-turn identity, settings-source discovery, JSONL rotation, out-of-order timestamps, remote divergence, and agent session restart. The terminal fakes expose lost replies after a successful create, duplicate groups, recurring and restored ids, a changed server instance, lost events, renamed labels and clobbered tokens, a silently ignored unknown parameter, a success reply with surviving processes, a growing process set, and an external workspace holder.

## Integration-only surfaces

The real `jj`, `gh`, Claude Code, Codex, the ratatui terminal loop, real Herdr at the pinned candidate build, real OS process inspection behind `ProcessSupervisor`, and the fsnotify watcher are smoke-tested or integration-tested. The Herdr integration runs against a disposable dedicated server and never the user's default Herdr server; its unproven gates are listed in [Terminal runtime](13-architecture/terminal-runtime.md#what-exists-what-kiki-builds-what-herdr-must-add). Each shipped harness's integration is still a release gate. For Claude Code, the gate covers exclusive `PreToolUse` settings isolation, stable model-turn and tool-batch identity, concurrent hook behavior, and `PostToolBatch` completion. For Codex, it covers `CODEX_HOME` isolation with kiki's hooks pre-trusted, the serial-dispatch proof, byte-identical visibility of deny payloads, and `Stop`/`SessionStart` lifecycle behavior. An upstream version that fails its probes uses hard restart or is unsupported; it is never modeled optimistically. Core interpretation logic belongs in deep-module tests against fakes.
